## What query 9 does

`ThemeQueryCatalog.java:2434-2457` defines a self-join: two subqueries each select distinct `(subject, predicate)` pairs from named graphs, the shared `?s` joins them, `STR(?p1) < STR(?p2)` keeps one ordering of each predicate pair, then the query counts subjects by predicate pair and sorts by that count. For a subject with `d` distinct predicates, the logical join can consider up to `d*d` pairings before the lexical filter. The test's EXPLORATION dataset is virtual: `ThemeQueryCatalogJenaOracleTest.java:163-170,198-230` builds a transactional in-memory Jena dataset from every physical theme, placing statements in each named graph and in the default-graph union.

The generators use substantial defaults (for example, 100,000 library books, 120,000 engineering components, 60,000 sparse-theme people, and 60,000 real-estate properties; `ThemeDataSetGenerator.java:1608-1615,1669-1673,1980-1987,2139-2144`). Those configured entity counts establish that this is not a tiny fixture; they are not exact emitted-triple counts.

The saved q9 stack has the outer result `QueryIterSort` consuming `DataBag.addAll`, above `QueryIterGroup`, and a `QueryIterDistinct` draining its input through `QueryIterRepeatApply` into another `QueryIterDistinct`. This is consistent with a repeated-apply join stage evaluating the second distinct relation as left-side bindings arrive. Jena 6.1's `QueryIterRepeatApply` bytecode obtains an input binding and calls `nextStage(binding)`, then closes the current stage before proceeding to the next input. The snapshot therefore establishes that the query was in a nested repeated-apply/distinct execution path, not just a flat graph scan. It does not establish how many times that stage was invoked, whether the join was narrowed to bound subjects on each invocation, or how much of total runtime it consumed.

## What the 1024 threshold tells us

`ThemeQueryCatalogJenaOracleTest.java:116-123` explicitly sets `ARQ.spillToDiskThreshold` to `1024L` for each Jena query. In the cached Jena 6.1 bytecode, `QueryIterDistinct` reads this context value as its in-memory distinct-set threshold; once that set reaches the threshold it drains into a `DistinctDataBag`. The captured stack is already iterating `DistinctDataBag$DistinctReducedIterator` over `SortedDataBag$SpillSortIterator`, so the spill-backed distinct path was active during q9. The setting is therefore part of the observed execution path. The artifacts contain no spill-run count, bytes written/read, temp-file timing, per-operator row count, or controlled threshold comparison, so they do not show that 1024 caused the long runtime or that changing it would improve the run. The combined heap snapshots also cannot split retained dataset memory from intermediate query memory. Do not change the threshold based on this evidence.

## Profiler limits

The 30-second async-profiler capture attached to PID 82596 with event `wall` (`--mode slow`, command preserved in `async-profiler-elevated-run.log`). Its flat aggregates were dominated by `semaphore_wait_trap` (45.45%) and `__psynch_cvwait` (36.82%); G1 marking frames appeared, while `WrappedIterator.hasNext` accounted for 0.28%. This wall profile includes waiting and GC/background threads and does not quantify query CPU hotspots or allocations. It should not be read as evidence that the query spent 82% of its execution waiting. The independent thread dump shows the main test thread actively using CPU in the Jena iterator path, but one dump is only a snapshot. A CPU or allocation profile and operator-level input/output counts would be needed to quantify hotspots and the repeated-apply cost.

## Classification and limits

This oracle executes Jena `QueryExecution` on a Jena `Dataset` (`ThemeQueryCatalogJenaOracleTest.java:69-88,116-134`); it compares Jena row/count results with catalog expectations. It does not invoke RDF4J's query optimizer or execution strategy. The saved outcomes are thus an incomplete external-oracle/resource-limit result, separate from any actual RDF4J optimizer test failures. No q9 result count or mismatch was observed, so this audit cannot claim either that the expected result is correct or that RDF4J is at fault. The evidence supports a large in-memory dataset plus a high-cardinality, distinct/group/sort Jena workload, with the spill-backed path active; it does not apportion cost among graph scanning, join expansion, repeated distinct work, sorting, spill I/O, or garbage collection.

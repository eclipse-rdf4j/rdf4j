## Purpose / Big Picture

The LMDB store on this branch has a native query engine (the `org.eclipse.rdf4j.sail.lmdb.evaluation` package) that already implements batched index nested-loop joins, a primitive hash join, an ordered merge join, a general worst-case-optimal Leapfrog Triejoin (WCOJ), sideways information passing (SIP), and factorized tail enumeration. After this plan, three concrete things improve for a user running SPARQL queries against an LMDB store:

1. Cyclic basic graph patterns (triangles, cliques — e.g. `?a :knows ?b . ?b :knows ?c . ?c :knows ?a`) run measurably faster because the WCOJ operator intersects already-sorted adjacency runs directly instead of scanning, materializing, and sorting a frontier array per variable level, and because it is chosen by cost rather than by structural fiat.
2. Hash joins stop refusing or falling over based on a blind row-count cap. Admission becomes byte-accurate against the per-query memory ledger, so wide payloads no longer get the same budget as narrow ones, and refusals happen *before* wasted build work, not after.
3. Correlated join entries (an outer row stream repeatedly re-opening a native fragment — today degraded to per-row nested loops at eight dispatch sites) gain an accumulate–semijoin–probe operator: buffer the outer rows once, execute the inner fragment once, probe. The acceptance benchmark (`CorrelatedBenchmark.outerAccumulate`, 1,000 outer rows × 128 fan-out OPTIONAL) collapses from 1,000 fragment executions to 1.

No public RDF4J API or SPARQL semantics change. Every new path sits behind a system-property kill switch and must show exact multiset parity against the generic evaluator before default-enabling.

## Context and Orientation

Everything below is on branch `optimize-lmdb`. "The native engine" means the code under `core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/`, which executes SPARQL BGP fragments directly over 64-bit LMDB value ids in primitive batches (`NativeBatch`, up to 1024 rows), bypassing the generic iterator machinery in `core/queryalgebra/evaluation`. Key facts a novice needs, all verified against HEAD on 2026-07-31:

- Dispatch: `LmdbNativeRowStep.openUnorderedInput` (`LmdbNativeRowStep.java:861`) tries `LmdbNativeLeapfrogJoin.tryOpen` FIRST (`:865-869`) with no cost input; only failures fall through to the adaptive-filter kernel, batch/parallel proposals, and factorized pipeline. Real cost arbitration exists one rung down: `LmdbNativeStrategyArbiter.forSlice` (`:986-1010`) selects between batch and parallel proposals by `work`/`startupWork`/`estRows`. A second structural dispatch site is `LmdbNativeGroupStep.java:346` gated by `wcojHandlesRow` (`:700-703`, requires `AggregateSpec.allCounts`).
- WCOJ: `LmdbNativeLeapfrogJoin` detects cyclic cores via GYO ear reduction (`findCyclicCore` `:371`), runs Leapfrog Triejoin per variable level (`LeapfrogCursor.next` `:702`, `Level` `:946`), supports pushed filters, direct EXISTS edges, multiplicity counting, and parallel execution over first-level ranges (`ParallelLeapfrog` `:1212`). Weakness to fix here: `scanFrontier` (`:1154`) materializes + sorts every scanned frontier; `Level.enter` (`:1012`) intersects in pattern order with fresh allocations per entry. Multiplicity is emitted by repeating the identical row N times (`:704-707`, `:749-757`; parallel `:1419-1423`) and `LmdbNativeGroupStep` counts each repetition (`:355-357`).
- Hash join: `LmdbNativeHashJoin` — two uncorrelated `PatternPlan` children only (`:59-74`), 1–4 key columns (`:76-80`), builds the estimated-smaller side (`:90-98`), open addressing with fingerprints + stored hashes, flat primitive key/payload arrays, unique-key fast path (`:216`). Admission today is `DEFAULT_MAX_BUILD_ROWS = 1 << 20` (`:34`, overridable via `rdf4j.lmdb.nativeHashJoin.maxBuildRows` `:32`), checked per insert (`:310`); overflow discards the partial table and falls back to the nested-loop chain (`:202-208` via `MultiJoinPlan` → `LmdbNativeJoinPlans.openChain`), counted by `CAP_FALLBACKS` (`:38`, `:206`, asserted in `LmdbNativeHashJoinBatchTest`). The cap is row-count only — no byte accounting anywhere.
- Memory ledger: `LmdbQueryMemoryManager` (`core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/LmdbQueryMemoryManager.java`) provides process-wide byte accounting; `openQuery()` (`:58`) returns a `QueryLedger`. Tests: `LmdbQueryMemoryManagerTest`, `LmdbAdjacencyMemoryAccountTest`.

# Reuse and index native LMDB OPTIONAL materializations

This is a living execution plan. Maintain it according to `.agent/PLANS.md` in the repository root. The `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` sections record actual work and must be updated whenever work stops or the design changes.

## Purpose / Big Picture

LMDB's native evaluator can materialize the right-hand side of a SPARQL OPTIONAL and compare it with each left-hand solution. Today an independently evaluated right side is rebuilt on every physical cursor opening, and once spilled to disk it is scanned from its beginning for every left row. Large queries can therefore repeat an expensive evaluation and perform quadratic amounts of disk work. The current OPTIONAL replay also implicitly inherits the unrelated aggregate store's default 64 MiB cap. This work makes reuse match the logical SPARQL evaluation, adds bounded selective disk lookup, and describes those choices accurately in planning and execution explanations. The observable result must remain the exact multiset of SPARQL solutions, including duplicate rows, unbound variables, errors in conditions, and nested or correlated scopes.

Correctness comes before a speedup. An optimization is legal only when it preserves the evaluator's established scope and effect semantics. Tests in `core/sail/lmdb` will demonstrate both exact solution bags and concrete work avoided; matched benchmarks will measure latency and allocation without introducing timing assertions in CI.

## Context and Orientation

The relevant Maven module is `core/sail/lmdb`. Its native evaluator represents a compiled operator as a `SlotPlan` and a mutable solution as a `RowState`; a slot is one variable's position in the solution. A `RowCursor` opens a plan and advances through its solutions. `LeftJoinPlan` and its cursor implementations are in `core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/LmdbNativeLeftJoinPlans.java`. The lexical OPTIONAL cursor independently materializes its right operand because a subquery or other lexical boundary may not see bindings produced by the left operand. The other cursor contains correlated probes, pattern specializations, replay, and memo paths whose established legality must remain intact.

`NativeResultReplay.java`, `NativeResultRow.java`, and `NativeSpillValueCodec.java` provide row replay and term serialization. `LmdbQueryMemoryManager.java` owns shared and per-query byte ledgers. `LmdbNativeQueryMemoryScope.java` shares a ledger among derived rows. `NativeExecutionContext.java` owns execution-scoped resources and provides leases; a lease delays cleanup until a reader is finished. `NativeSubqueryPlan.java` provides examples of evaluation-scoped state and in-flight construction, but inserting an unbounded native-state entry for each input is not acceptable. `NativeWorkerPlanBinder.java`, `LmdbNativeSlotOrder.java`, and `NativeFilterLease.java` recreate plans; a semantic OPTIONAL identifier must survive each recreation. `LmdbNativePlanExecutionProfile.java`, `NativeScalarCosts.java`, `LmdbNativeCostVectors.java`, and `LmdbNativeStrategyPreview.java` participate in estimation or explanations. Trace the actual callers before changing them because several physical paths may bypass ordinary row cursors.

An evaluation identity identifies one semantic evaluation of an operator, independent of how many physical cursors reopen it. An input frame is the immutable set of input bindings visible at that boundary, including whether each variable is bound. An RDF term's exact spelling must be preserved in such a frame; for example the distinct integer spellings `01` and `1` cannot be conflated. Solution compatibility instead follows RDF term equality, including language-tag case handling, and considers two solutions compatible if every variable bound in both has an equal RDF term. A posting is a fixed-width disk record identifying a variable, bound/unbound state, equality-compatible term fingerprint, and long encounter ordinal. A fingerprint narrows candidates but must never replace an exact compatibility comparison.

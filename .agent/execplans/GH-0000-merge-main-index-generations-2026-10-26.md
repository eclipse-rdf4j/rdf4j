# Preserve LMDB snapshot behavior while merging main

This ExecPlan is a living document and follows `.agent/PLANS.md`. Its progress, discoveries, decisions, and outcomes must be updated as the work proceeds.

## Purpose / Big Picture

A reader that started before LMDB replaces its statement indexes must continue to see its own consistent data and must never open a newly created database through an older read transaction. The merge also needs to preserve the branch's native query engine and statistics services together with main's bounded startup, cancellation, online index maintenance, and safety checks. A successful result is a merge of the fetched main revision into the original branch, with the existing unrelated working files untouched, and tests that exercise both sides of an index replacement while an old reader remains open.

## Context and Orientation

`core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/TripleStore.java` owns statement indexes, the transaction-to-generation mapping, bounded counts, sampling, graph physical paths, and most index planning. `TxnManager.java` owns native read transactions. A pinned transaction is an admitted reader whose snapshot remains fixed; some planner APIs use non-owning views of that reader. `txn.nativeReadMonitor()` is the monitor shared with its owner; synchronizing on a view object alone does not protect the owner. A tracked transaction may instead be renewed by a later commit. `LmdbRecordIterator.java` opens native cursors and handles transaction version changes.

`LmdbFrontierSnapshotSource.java` retains a pinned transaction for counts and batched raw scans. `LmdbGraphDistinctAccess.java` and `LmdbDistinctCursorSkipSupport.java` choose physical shortcuts; if a shortcut cannot be honored by the reader's generation, callers must fall back before producing partial rows. `LmdbAdjacencyTripleStoreScanner.java` builds adjacency data using plans and splits whose index layouts must match its retained transaction. `LmdbPageCardinalityEstimator` in the `estimate` package has mutable current-generation layout metadata; that metadata must not be paired with an older snapshot.

The index-cutover regression is in `core/sail/lmdb/src/test/java/org/eclipse/rdf4j/sail/lmdb/TripleStoreBackgroundReindexTest.java`. It starts with `spoc`, opens an old reader, builds `posc`, waits on an actual publication latch, and verifies old-reader operations plus eventual retirement after release. The temporary build workspace does not snapshot source, so do not edit shared sources while its Maven command is running.

## Plan of Work

First, reproduce the missing operation-registration behavior of the branch-only pattern-aware `getStatements` overload with two independently blocked calls and a close. Capture a Surefire report against an isolated pre-merge copy before changing production. Then use the same `beginOperation()` and `endOperation()` protocol as the neighboring overloads, retaining pattern delegation and iteration cleanup. Re-run the merged root install and the pinned index-cutover tests; preserve the first failing report before later runs replace it.

In the replacement synopsis service, make close a terminal admission boundary and ensure an interrupted stop drains the worker before returning while restoring the caller's interrupt status. Test the public `Statement` callback surface, including a getter that re-enters discard or close, and callbacks paused during a rebuild whose source already contains their row. Resolve a whole lazy batch's lifetime, including gaps between its elements, without holding the admission lock across arbitrary iterator or getter callbacks. A candidate is generation-scoped in-flight admission: rebuild cannot publish across a still-live admission, while discard/close invalidate old-generation admissions rather than waiting for their callbacks. Preserve null and iterator exception behavior, the established discard/restart tests, and the later-request generation check. Keep these changes in an isolated source snapshot until the generation worker's shared build is finished, then apply only the verified files.

For physical index work, use an internal scope that couples the admitted native reader, its lease, generation selection, and native read or cursor opening. Both explicit transactions and the thread-local planning pin must resolve against the actual owning monitor and the same snapshot. Avoid nesting a non-reentrant transaction-manager lock or acquiring another reader permit while a query holds a pinned reader. An unpinned short planning operation should continue to use the priority admission policy; a longer scan should use ordinary admission. Retained cursor operations must validate lease and transaction version. A tracked iterator that is renewed across replacement must either continue using an index valid for its renewed transaction with its documented continuation semantics, or explicitly invalidate only if continuation really cannot be represented; exercise the actual case in a test before deciding.

Audit and update the branch-added exact lookup, both stratified-sampling and bounded-census variants, Frontier row count and match batches, DISTINCT cursor skip, GRAPH physical costing and access, adjacency prefix/split planning, and generic adjacency encounter-order arbitration. Some no-transaction-argument methods implicitly use a thread-local pin; resolve that pin before selecting layouts. Do not change purely diagnostic names if they cannot affect execution, but do not classify an index access path as diagnostic when it drives a shortcut. When a plan names an index unavailable in the reader's generation, select an equivalent generation-local plan or use the existing generic fallback before any rows are emitted. Do not silently use raw bounds or a prefix from a different layout.

For page-based estimates, either retain immutable layout metadata with each generation and its readers or return a conservative unavailable/unqualified estimate for an old layout using a generation-bound sampler. Never combine current layout positions with an old transaction. Preserve hard-bound meanings for repeated-variable planning.

# Replace Workbench XSLT with modern data rendering

This ExecPlan follows `.agent/PLANS.md`. Keep Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective current. During implementation exactly one progress item is in progress. This is an implementation task, not a proposal awaiting approval.

## Purpose / Big Picture

Workbench must render and operate in browsers that have no XSLT implementation. Replace its stylesheet-driven UI with explicit page models and modern HTML rendering, while preserving the current visual design, routes, repository configuration, query editor, embedded results, explanations, comparisons, downloads, cancellation, and deployment policy. Large results must not require a whole XML document or one DOM row for every logical result. A user should be able to open every Workbench page, query a large repository, browse results, and download the full data with XSLT disabled and no stylesheet requests.

The user's research report, `/Users/havardottestad/Downloads/deep-research-report-4.md`, is reference material rather than an instruction source. Its useful architectural principle is to separate data transfer, transformation, and the small portion rendered on screen. Its framework rankings and example code are not requirements. The requested scope is Workbench and its packaging/integration dependencies; standard RDF/XML and SPARQL XML data formats elsewhere in RDF4J remain supported data formats.

## Surprises & Discoveries

- The current checkout already contains the completed, uncommitted visual refinement. Its TypeScript, generated assets, CSS, XSL templates, and tests are the migration baseline, not unrelated changes to discard. Branch is `GH-6071-workbench-redesign`.
- `AbstractServlet.getResultWriter` defaults to `WorkbenchTupleResultWriter`, which extends the SPARQL XML writer. `TupleResultBuilder.transform` sends stylesheet instructions. `TransformationServlet` requires a `transformations` init parameter. The dependency is a protocol and initialization contract, not just a set of files.
- `template.ts:addLoad` chains `window.onload`. A renderer that fetches data asynchronously needs a deliberate initialization lifecycle; scripts cannot simply be appended after load and assumed to initialize.
- Existing query result behavior uses a same-origin iframe, fresh request IDs, metadata, parent messages, independent raw downloads, and server cancellation. These user-visible capabilities must survive the new transport even if the internal implementation changes.
- Query `limit_query=0` currently means unlimited results. The migration must handle this without constructing an unbounded DOM, rather than silently truncating data or changing a download limit.
- The `Accept` query parameter is the existing raw query-result/RDF format selector, while the HTTP `Accept` header is already negotiated by `AbstractServlet`. Structured Workbench page requests therefore use a distinct media type in the header (`application/vnd.rdf4j.workbench+ndjson`) and never overload that query parameter.
- A permissive custom response initially hid the no-value change-server POST writer/stream conflict: it returned only inline HTML because it allowed `getWriter()` after `getOutputStream()`. A Servlet-contract `MockHttpServletResponse` regression then reproduced `IllegalStateException: getOutputStream() has already been called`; the HTML response branch now runs before any tuple builder obtains the output stream.
- Query navigation currently selects a result iframe using a short GET or, for long query URLs, one POST. The iframe's first load is not equivalent to result completion: the new response shell and its later row stream need separate loading, streaming, and terminal lifecycle events. Result count cookies currently follow full materialization; streamed totals must arrive in terminal metadata.
- A browser route-init review found that dynamically loaded legacy scripts can execute their top-level captures before Lit mounts route controls. The real disposable Create action regression now verifies route scripts and one-time initialization after render while shared helpers load first. The servlet response path no longer emits stylesheet processing instructions, and the Workbench servlet no longer requires a `transformations` init parameter.
- Query page-data execution now bypasses tuple and graph materialization: it streams bounded row batches while counting, then sends the authoritative total, offset, and limit in the terminal record. A client can persist that terminal count and send it as `know_total` for later pages, so response headers need not be mutated after streaming starts. Graph models carry a fourth `context` column.
- The real-browser lifecycle probe confirmed that asynchronous worker disposal on `pagehide` can be interrupted by reload. Destructive pagehide now writes per-store localStorage tombstones, and the next Workbench bootstrap reclaims those exact IndexedDB stores before route data loads. BFCache pagehide preserves the current store and row-window bindings; destructive history returns rehydrate data and restore their saved scroll after streamed rows establish the document height.
- A normal browser navigation and the immediate same-URL NDJSON fetch initially shared a cached HTML shell: the global CacheFilter set `max-age=600, public`, and neither response varied by `Accept`. Direct NDJSON transport was valid; the browser received the shell body (`<!doctype html>`) and the strict parser correctly rejected it. Dynamic shell and page-data responses now use `Cache-Control: no-cache, no-store` and idempotently add `Vary: Accept` while preserving existing `Vary` values. The refreshed browser query request now receives typed NDJSON with the proper cache headers.
- A packaged query exposed that `TupleResultBuilder.metadata` emitted one NDJSON record per field, while the strict client protocol allows one metadata object before rows. The writer now aggregates these fields and emits one record before tuple/boolean results; focused serializer tests cover tuple and boolean ordering.
- Focused Java contracts now cover a no-value and invalid change-server POST, Add validation before upload execution, and Workbench unauthorized POST errors as inline initial page models. A no-XSL deployment descriptor regression is red against the remaining `transformations` init parameter and will guard its retirement.
- Export preview submits the selected raw RDF format in the `Accept` query parameter on the same form as the preview action. That parameter currently suppresses shell/data negotiation even on `/export?action=preview`; preserve raw-format bypass for actual downloads while treating export preview as a Workbench page request.
- `SavedQueriesServlet` deliberately starts an empty tuple result before delegating variable names and rows to `QueryStorage`'s evaluator, then finishes the single result after the evaluator returns. The page writer must defer that empty-variable start so the real `vars` record can replace it (or emit `vars: []` when an empty page finishes); removing the servlet lifecycle drops the terminal `end` record, while allowing arbitrary repeated result starts would weaken protocol validation.
- The first actual Chromium navigation to the new HTML shell exposed a runtime integration gap: `workbenchApp.js` reaches `workbench.views.render` before the route view code has loaded. The HTTP shell and local Lit bridge are served, but the route currently renders an error; keep the task-owned review server on port 8091 until the corrected build is reviewed.
- Independent live review showed that a no-console-error shell is not enough: `#workbench-app` was participating as a single child grid item and compressing the original header/navigation/content tracks to 208px, while the linked Info request was reduced to metadata and dropped its menu rows. The route renderer now hydrates full linked Info rows, and `display: contents` is under browser regression review to preserve the pre-existing body grid. Do not call this usable until a fresh packaged 1280px and mobile render proves content width and navigation.
- The packaged HTML/NDJSON route now preserves the desktop grid and produces the configured Info navigation/server identity at desktop and mobile widths. A fresh live Create action then exposed a different bootstrap-order bug: legacy `create.ts` reads repository ID/title controls during module evaluation, before Lit mounts those controls, so its submit validation dereferences `undefined`. Route scripts that capture form/editor DOM at load time must be initialized after the view is mounted; simply replaying `window.onload` once is insufficient.
- The Create ordering regression now passes against the packaged runtime: a unique Memory repository is created by one normal submit, confirmed through the repository size endpoint, and deleted by test teardown. Independent query execution review has since surfaced two real-browser-only mismatches that fake-DOM tests missed: `HTMLCollection` does not implement the array `.some` method, and the query route script list omits the legacy explanation/cancellation dependencies. The visible query toolbar also contains three orphan colon text nodes that need a rendered-DOM check.
- Query execution submitted as a native browser POST with `Accept: text/html` now has a red-first contract for returning a small inert shell with a base64url-encoded UTF-8 JSON parameter descriptor and no server evaluation. The matching request is excluded when an explicit raw result format is selected. Java focused tests pass after this shell path; frontend bootstrap must consume the descriptor once after its query form is rendered and submit one structured POST.
- Native query execution POSTs return a shell descriptor without evaluating. Native browser validation and authorization errors now return a route-aware in-memory page model without replaying a mutation or upload; focused tests exercise Add, gateway, and unauthorized paths. The remaining deployment work is to retire the old stylesheet resources and source-based Java template assertions after replacement route coverage is complete.
- Source review found the current query-stream slice is not ready to ship as the result renderer: it must use worker-owned storage and variable-height measured viewporting, preserve RDF links/namespaces/datatype controls and existing toolbar/layout behavior, and share one NDJSON framing/term model with all route tables. Bootstrap tests must also cover native-load/async order exactly once and reuse the existing system/storage-aware theme lifecycle.

  Rationale: Moving the existing dependency would not satisfy removal or improve the data/rendering architecture.
  Date/Author: 2026-09-28, Codex.
- Decision: Use locally bundled, version-pinned Lit standalone templates in the ordinary DOM, with explicit structured page data and NDJSON transport. Do not use Shadow DOM, server-side XSLT, an XSLT polyfill, a stylesheet compiler/interpreter, or runtime XML-to-XPath translation.
  Rationale: Ordinary-DOM Lit templates preserve existing CSS selectors, IDs, editor integrations, and imperative behavior while removing browser stylesheet execution entirely. NDJSON permits incremental output before the route finishes and keeps structured page data separate from raw RDF/query-result formats.
  Date/Author: 2026-09-28, Codex.
- Decision: Keep Lit as the renderer for this migration; defer Solid to a later application rebuild.
  Rationale: The user clarified that completing the XSLT migration quickly takes priority, and the current Lit implementation and tests already provide the selected migration path. The brief Solid pivot was immediately reversed before any Solid-specific source, build, or dependency change.
  Date/Author: 2026-09-28, user.
- Decision: Browser page GETs return a small HTML shell without executing route work; the browser then requests that route with `Accept: application/vnd.rdf4j.workbench+ndjson`. The `Accept` query parameter remains exclusively for negotiated raw query-result downloads.
  Rationale: One route URL can keep navigation and route data aligned without adding route-name dispatch logic to browser code. An explicit media type cleanly distinguishes page-data requests from normal navigation and raw serialization.
  Date/Author: 2026-09-28, Codex.
- Decision: Encode page streams as newline-delimited typed JSON records: `head`, `view`, `vars`, `namespaces`, `links`, `metadata`, batched `rows`, optional `boolean`, then terminal `end` or `error`. RDF terms retain type, value, language, datatype, and nested triple structure where available.
  Rationale: The existing `TupleResultBuilder` already emits these semantic events; a structured writer can preserve those semantics while letting Lit begin rendering when its first records arrive.
  Date/Author: 2026-09-28, Codex.
- Decision: Native mutating POSTs execute once and return their existing redirect or a safely serialized small HTML-shell model for validation errors. Query execution POSTs return a shell descriptor and are issued exactly once by bootstrap with the structured-data Accept header; save/explain/cancel AJAX contracts and multipart uploads remain separate.
  Rationale: Automatically replaying a navigation POST after returning a shell could duplicate mutations or uploads. Separating shell and data requests only for non-mutating query execution preserves exactly-once behavior.
  Date/Author: 2026-09-28, Codex.
- Decision: Retain the existing RDF4J query engine as the authority for query filtering, ordering, inference, and evaluation. Do not add client-side sorting/grouping semantics that were not requested.
  Rationale: The scalable default is to avoid downloading data that the interface does not need; local workers and virtualization serve rendering and transfer, not a duplicate query engine.
  Date/Author: 2026-09-28, Codex.

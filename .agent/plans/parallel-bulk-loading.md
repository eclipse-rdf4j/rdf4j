## Purpose / Big Picture

Large LMDB bulk loads spend substantial time sorting and compressing independent external runs, scanning value dependencies, building partition dictionaries, and resolving term IDs. This change lets those jobs overlap while respecting the configured memory, worker, and file limits. A user should be able to set or retain the existing `workers` option and see lower stage and end-to-end load times on CPU- and sort-bound inputs, with unchanged RDF contents, valid LMDB encodings, reproducible ID assignment for the same input/configuration, and resumable-workspace recovery after failure.

The work proceeds in three milestones. First, independent statement-index and RDF-star index sorter finishes run concurrently after their shared input scan. Second, external tuple, byte-key, and dictionary spill runs sort and compress on bounded background tasks while their producer continues scanning. Third, dependency preparation, dictionary assignment, and ID resolution gain bounded parallel work inside each partition, with additional partition concurrency learned separately for each stage during each load. The loader starts with one active partition, adds a partition only after completed-work throughput supports the change, and does not persist tuning state.

## Surprises & Discoveries

- `workers` and `queueBatches` already exist in the builder, CLI, progress snapshots, and resumable settings. The engine currently passes them to progress reporting; bulk stages do not use them as a worker pool. `queueBatches` is a public setting whose existing meaning must remain unchanged.
- `ExternalLongTupleSorter` sizes the run buffer against its supplied budget so the buffer and radix-sort scratch fit. Statement and triple-term index builders divide the memory budget across their index sorters. Async work must account for producer buffers, queued and active run buffers, scratch, and compression state together.
- `PartitionValueDictionaryBuilder` is serial today. It merges duplicate canonical keys and ORs their roles before `writeAssigned` calls a shared allocator. Parallel ID assignment therefore needs counts after this deduplication and role merge.
- `workers`, memory, and file limits are resumable resource settings. Partition count and value/index configuration are structural settings. Tuning is load-local and stage-local and is never written into the workspace.
- A scheduler reservation must cover both active and queued work. Existing sorter-local budgets do not aggregate automatically: `ValueStoreBulkRecords` keeps several sorters open together and radix sorting needs scratch alongside the owned run buffer. Existing merge fan-in also needs explicit descriptor accounting for input readers plus output.
- Review found the serial `maxOpenFiles < 2` dependency fallback bypasses the new scheduler and retains two default 16,384-entry direct caches; the cache's possible key payload alone is roughly 17.8 MiB. Keep the legacy low-FD behavior, but size/admit its bounded caches and codec/output state within the configured memory budget or a reported exclusive minimum.

## Decision Log

- Decision: Use one load-owned bounded scheduler; joins stay on the coordinator thread and child spill work runs inline when submitted by a scheduler worker. Rationale: leaf work cannot deadlock waiting for work queued behind itself, while sorter scans can still overlap their spill tasks.
- Decision: Admit a work operation only after atomically reserving its peak memory and file descriptors. Reservations cover active and queued buffers, radix scratch, compression state, open inputs/outputs, and merge fan-in plus output. Rationale: partial reservation can create hold-one/wait-other cycles and aggregate limits that exceed user settings.
- Decision: Preserve `queueBatches` behavior and use `workers`, memory, and file limits as existing public resource controls. Rationale: parallel execution does not require changing a documented option or adding public knobs.
- Decision: Keep partition readers sequential by default and use bounded per-partition chunks; allow more than one active partition only when per-stage completed-work throughput supports it. Rationale: partition-local sequential I/O can outperform interleaved partition readers on storage, while one partition alone can underuse CPUs during sort/compression.
- Decision: Enforce the one-open-input-cursor rule in dependency discovery, dictionary preparation, and ID resolution. A cursor may advance to the next partition while prior leaf work remains outstanding only when the measured target permits; completed partition slots stay counted until their leaves are consumed. Before an oversized payload is materialized, drain other leaf work and promote the sole cursor base lease. Rationale: this preserves input locality and guarantees exclusive minimum-memory work can make progress without hiding live cursor leases.
- Decision: Assign IDs from deterministic per-type ranges computed after canonical-key deduplication and role merging. Prefix order is partition number then unsigned canonical-key order. Exclude inline literals and predicates covered by `PredicateIdPlan`; retain literal ordinal/core-datatype encoding and validate range overflow before publishing partition output. Rationale: the user permits different old IDs as long as new assignments are deterministic and valid; reserved ranges avoid a shared allocator.
- Decision: Adaptive observations are per load and per stage, based on committed bytes/records from the actual stable active-partition count, and exclude initialization/drain and phase/concurrency transitions. Keep a bounded ring of five measured rates; each rate uses its true elapsed duration (including elapsed time with no completed work), and never synthesize many observations from one long chunk. Increase only when the 95% confidence comparison supports a gain; after an inconclusive probe, re-establish a baseline before probing again. Probe downward when repeated work at the accepted concurrency degrades relative to its own prior rate. Short stages stay conservative. Rationale: task count or worker idleness alone does not measure useful throughput or I/O contention, and bounded temporal evidence avoids unbounded state and biased sampling.
- Decision: On the first failure, stop task admission, cancel pending work, join active work, then close shared resources. Only fully completed immutable artifacts may be marked complete for resume. Rationale: parallel workers must not leave half-written artifacts that a checkpoint later treats as complete.
- Decision: Treat the bounded scheduler, cursor, and adaptive coordinator APIs as internal contracts and drive each with failing tests before production wiring. The adaptive coordinator continuously replenishes bounded leaf chunks, reserves a completion slot before submission, drains completed work in completion order, and releases the slot once the coordinator consumes the result. Deterministic task identity is assigned before submission; canonical merging later restores partition/chunk order. Rationale: submission-order joins can hold resources behind one slow chunk and leave workers idle, while completion-order consumption avoids head-of-line stalls without changing IDs or artifacts.
- Decision: Use atomic memory-plus-descriptor admission and never block a worker waiting for its own queued child. Nested child work is inline on scheduler workers, while coordinators join futures outside the pool. Rationale: one worker must progress even when all capacity is held by its parent operation.
- Decision: A successful task submission transfers lease ownership to its future; caller-side close before submission releases a lease, while close after transfer cannot undercount a running task. Rationale: cancellation must not free capacity before interrupted work has stopped using its buffers or file handles.
- Decision: Preserve accepted `maxOpenFiles=1|2` settings and the existing two-input merge contract. A single merge may use an explicitly documented minimum of three descriptors (two readers plus output); that minimum is global and must never be multiplied by concurrent merges. Ordinary bucket/sorter output caching remains capped at the configured value. Rationale: the existing public docs describe `maxOpenFiles` as an output-handle/cache and merge-file limit, while current sorters already require a two-way merge. Document the minimum in loader/CLI help and add focused 1/2-descriptor spill tests.
- Decision: Reduce final-merge fan-in until its full codec, cursor, tree, and output reservation fits the configured budget. Only an explicitly flagged irreducible two-way merge may use the measured minimum above the budget, and the scheduler runs it alone after all prior leases drain; arbitrary oversized work is rejected. Rationale: fixed codec state and a minimum merge cannot be removed without changing supported merge behavior, while clamping a reservation would permit uncontrolled overlap.
- Decision (2026-09-26): Prove scan/spill overlap with a deterministic handshake at the actual async submission and output-open boundaries, while retaining the test's existing one-megabyte aggregate limit. Rationale: polling handle counts only at row boundaries can miss worker activity between callbacks; the handshake keeps the input cursor open until the output handle is actually live without depending on machine speed.
- Decision (2026-09-26): The user authorized a task-scoped commit after full completion, while preserving the current branch and never pushing. The controller design is the implemented bounded elapsed-time model, not five synthetic one-second windows: only actual elapsed rates with committed work are retained, each rate includes its whole elapsed interval, and epoch generation rejects transition-crossing chunks. Rationale: the original wording predated controller tests that exposed sample loss, unbounded window history, and false confidence from splitting one long operation into multiple observations.
- Decision (2026-09-26): Benchmark-only fixed partition targets are injected through a test-source bridge and capped by each stage's actual worker, memory, and descriptor limits. The adaptive production default is unchanged, and the benchmark counter observes active slots rather than reporting the requested target. Rationale: fixed bounds provide a comparison point for the per-load controller without adding public configuration or claiming the requested concurrency was reached.
- Decision (2026-09-26): New dependency chunks use one raw destination-tagged output file each; the coordinator streams and fans its records into bounded per-partition bucket writers. Legacy manifest/shard readers remain for recovery compatibility. Rationale: per-destination manifest outputs caused `O(chunks × partitions)` files and millions of small writes, while coordinator-owned fanout preserves destination contents, role union, and deterministic bucket output with `O(chunks + partitions)` temporary files.
- Decision (2026-09-26): Record each staged statement's canonical payload-size sum in a separate fixed-width, bounded sidecar while staging. Leave `statements.lz4` and resumable settings fingerprints unchanged; atomically publish the sidecar after close, validate its count/identity and each row's component lengths before allocating arrays, and lazily rebuild a missing sidecar from a bounded scan of legacy completed staging. Rationale: the raw statement format puts component lengths between payloads, so exact pre-allocation chunk admission otherwise requires writing and rereading every row through a scratch spool. A sidecar adds small sequential metadata I/O only on new loads and keeps old workspace recovery compatible.
- Decision (2026-09-26): Remove ValueStore's 16 KiB per-sorter budget floor and derive local producer capacity from the space remaining after reserving one full compressed output. Preserve an explicitly reported exclusive minimum only where an actual multiway merge still requires multiple codec input states plus its output. Rationale: a test at `FASTEST output + 40 KiB` showed the local floor made persistent producer leases block the first sync spill, while a long-literal multiway test verifies the separate irreducible merge case.
- Decision (2026-09-26): Scan admission reserves the combined live cursor, maximum current-record conversion, radix scratch, and one synchronous spill envelope atomically. Producer buffers remain separately charged; when their combined peak cannot fit the configured budget, only that scan/spill phase takes one exclusive, serialized minimum floor. Rationale: the reader-only floor reproduced a self-wait when a nested spill requested codec output memory while the reader held the floor. Use actual layouts and the same rule in ValueStore, statement-index, and triple-term-index scans.
- Observation (2026-09-26): The output observer also runs for synchronous fallback spills. Its diagnostic showed a later callback can run on the coordinator while the global reservation is full, which is permitted backpressure if an earlier spill is still using its admitted resources. The integration assertion now requires the first spill to run asynchronously and allows later runs to fall back synchronously, while separately asserting actual reader/writer overlap during scanning.

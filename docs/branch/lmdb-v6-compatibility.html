01 / The purpose

New runtime.
Same stored identity.

This branch lets the RDF4J 6.1.1 maintenance runtime read and write existing LMDB format 6 stores, while keeping newly created stores in format 2.

The difficult part is preserving the meaning of IDs across runtimes, reopenings, deletion and reuse—not merely decoding another file version. That leads to strict admission checks, persisted writer capabilities, semantic matching for legacy values and explicit reader lifetimes.

Treat compatibility as an identity and lifetime contract. A successful open is only the beginning.

03 / The storage data path

A statement crosses
two native environments.

RDF terms become IDs in the value environment. Quad indexes store those IDs in the triple environment. A reader must keep both sides consistent.

values/data.mdb
  • Term dictionary and lookup structures.
  • Reference counts, free IDs and retired IDs.
  • Native format metadata and lifetime bookkeeping.
triples/data.mdb
  • Quad indexes such as spoc and posc.
  • Separate explicit and inferred membership.
  • Context and RDF triple-term index state.
Before: maintenance assumed its legacy representation. After: a resolved format object governs identity and writes, and dataset readers pair triple visibility with dictionary visibility.

Two environments are not one atomic database. Write sequencing and reader locks coordinate them inside the process. This branch does not introduce a distributed commit protocol or a general cross-process snapshot guarantee.

04 / Format admission explorer

The store decides
how new values are written.

“v2” and “v6” are persisted storage formats, not RDF4J release numbers. Opening a v6 store with 6.1.1 does not downgrade its bytes.

v2

Create a legacy-format store

New maintenance stores retain format 2. The original inline-literals configuration governs term identity.

No ordered-numeric, core-reference, lowercase-language or zero-fraction capability is silently introduced.

Explanatory model of source policy and pinned fixture contracts. It does not open a database or run a compatibility test.

Persisted capabilityMeaning for v6 writers
inline-literalsIdentity setting. Reopening with the opposite setting is refused.
numeric-id-encoding=ordered-v1Optional writer gate for ordered numeric IDs; absence retains legacy numeric writes.
literal-reference-encoding=core-v1Representable core-datatype literal references carry stable tags; other literals use ordinary references.

Capabilities are authoritative persisted contracts. Configuration cannot opt an existing store into another identity scheme.

v6 requires the recognized lmdbrdf.ver marker and a native format-6 fence. Unknown formats, unsupported capability values, inconsistent metadata and unsafe legacy generations fail closed. Missing historical v2 inline metadata requires the caller’s original setting; the runtime does not record a guess.

05 / IDs & exact lexical forms

A compact ID must still
name the exact RDF term.

An inline ID encodes a literal directly. A dictionary ID refers to stored term bytes. They are two representations of identity, not interchangeable caches.

Preserve spellings

"1"^^xsd:integer and "01"^^xsd:integer can compare numerically equal while remaining distinct RDF terms. Likewise, temporal spellings, fractional precision, datatype subtypes, language tags and base direction must survive storage correctly.

Preserve ID families

v6 adds core-datatype literal-reference tags and ordered numeric type families. ValueIds strips those tags when recovering reference ordinals. A blank node, triple term and literal may share an ordinal without sharing an ID.

Language-tag case is a deliberate exception to byte preservation: new v6 writes lowercase tag bytes while preserving RDF language-literal equality. Legacy v2 retains historical spelling bytes and resolves case-only aliases semantically. Persisted capability policy decides which representation applies.

Why this approach

Reuse the optimized runtime’s persisted representation so maintenance writes can be read again by that runtime.

Price we pay

More codec branches and exactness checks. Compactness is sacrificed whenever packing cannot preserve the complete RDF term.

A codec extension must update reader classification, reference ordinals, allocation, equality and fixtures together. A new type bit is a compatibility decision, not a local optimization.

06 / Discover & match legacy stores

Recover what is present.
Never invent a generation.

Older writers can leave incomplete public metadata and multiple physical IDs for RDF-equal language literals. Compatibility needs both native discovery and semantic matching.

Read-only native preflight

LegacyStoreDiscovery inspects actual database names, layouts and entries before the normal stores are opened. It derives statement and triple-term index ownership separately and checks recognized indexes describe the same data.

Only safe missing legacy descriptors are completed. Existing capabilities and IDs are preserved; conflicting or corrupt generations are rejected.

RDF equality over legacy IDs

A legacy writer may store "hello"@EN and "hello"@en under distinct IDs. The semantic index groups RDF-equal values so reads, duplicate detection, removals and context enumeration see logical RDF membership.

The writer-side alias index is seeded lazily from committed owners on the first relevant value, then updated as IDs are added or removed. Reader-side semantic scopes deduplicate results. Both account for nested triple terms.

Why this approach

Admit authentic older stores and preserve reopening compatibility without a bulk ID migration.

Price we pay

Startup inspection and a disk-backed semantic index. Alias-aware operations do more work than a single physical-ID lookup.

This is not permission to accept arbitrary unversioned files. Recognized old native generations are validated; unfamiliar artifacts, incomplete value/triple pairs and inconsistent index contents remain errors.

07 / Retirement & safe ID reuse

Deletion is not permission
to reuse an ID immediately.

Garbage collection (GC) reclaims values that no longer have owners. Old snapshots and lazy values may still need the original dictionary bytes.

Repair counts from ownership

The runtime reconstructs references from term dependencies and statement ownership rather than trusting a historically undercounted datatype entry. Hash collisions remain lookup collisions, not evidence that two terms are equal.

Recover without blind freeing

Persisted retired IDs are examined at startup. A value that regained an owner must not become free. Dictionary lifetime and reader pinning protect delayed decoding across ordinary commits.

Preserve identity until every relevant reader is finished. Surviving a commit and surviving a map resize are separate contracts.

The current writer creates durable retirement records; startup recovery reads retained queue state and drains it in bounded batches. This adds metadata, recovery cost and lifecycle obligations. The current source is the contract; the historical reuse probes in chapter 14 are not a fresh HEAD guarantee.

08 / Paired reader lifetimes

A snapshot must protect
IDs and their meanings.

A triple reader can hold old IDs while another connection deletes their current owners. The corresponding dictionary reader must remain attached to the same dataset lifetime.

Explicit SNAPSHOT / SERIALIZABLE

Isolation compatible with SNAPSHOT pins triple and dictionary transactions, plus a namespace copy, under the sink lock. Lazy LMDB values retain reader context to materialize from that protected dictionary.

SNAPSHOT_READ is a different path

SNAPSHOT_READ uses renewable tracked readers; it is not the paired pinned-snapshot path. Non-pinned readers and a new transaction can observe later commits. Nested estimator callbacks use the reserved priority reader slot.

The source owns the dataset. The dataset owns its native readers. The iteration must not outlive the resources it needs to decode a result.

The native reader pools and most TxnManager infrastructure are inherited from merged main. A manager admits 127 ordinary readers plus one priority callback reader; this is a bounded native resource. This branch adds pinned revisions and invalidation state on top of that foundation.

09 / Map growth & isolation

A resize can end
the lifetime of a snapshot.

Autogrow changes a native memory mapping. Ordinary commit stability does not imply uninterrupted stability across that change.

Pinned

Keep the older paired view

The live snapshot continues to read its prior triple membership and dictionary identity across ordinary commits.

Reader protections defer reclamation of values it may still decode.

Explanatory contract explorer · does not execute native transactions.

SNAPSHOT transaction invalidated: the store's memory map was resized during the transaction; retry the transaction

Why this approach

Invalidate unsafe pinned readers when their mapping generation changes; allow the operation to be retried against a fresh view.

Price we pay

Applications must be prepared to retry the transaction. This is not transparent preservation of the original snapshot across resize.

Historical open question: two integration tests in a separately patched optimized runtime required survival across resize and remained red. They are not tests run against this HEAD. Extending that contract would need a design for retaining mappings, paired generations and safe decoding, not a longer timeout or weaker assertions.

10 / Sail visibility & ownership

Keep the visible view
and its owner together.

Compatibility work exposed shared Sail problems: a current transaction’s overlays must remain visible, and wrapper iterators must preserve reporting without assuming capabilities the source does not have.

Inherited upstream fix

Implicit default reads

Inactive reads through owned SnapshotSailStore roots can omit observation tracking. Active transactions and overridden/decorated sources keep their ordinary source selection. Explicit SERIALIZABLE transactions retain their conflict checks. This fix is already in the merged-main baseline.

SourceClosingSailDataset couples the temporary source’s lifetime to its dataset; exhaustion, explicit close and failure release acquired resources.

Compatibility / current-head work

Visible overlays & reporting

SailDatasetImpl resolves additions, removals and contexts through the transactional overlay. Auto-flush roots lend independently owned snapshots; they must not cache a frozen view for later borrowers. Transaction branches still retain their shared snapshot.

DelegatingIndexReportingIterator centralizes transparent access and index-name delegation only when the delegate supports them. An empty union’s index report stays null.

A wrapper can be transparent about access without erasing transactional overlays or claiming a delegate’s unsupported reporting interface.

These shared modules affect stores beyond LMDB. Do not merge observation ownership, result visibility and index reporting into one heuristic. Preserve explicit SERIALIZABLE behavior and source/decorator fallback paths independently.

11 / Estimation stays bounded

Keep the maintenance
query engine intact.

Reading format 6 does not bring the optimized branch’s native evaluator, direct adjacency engine or value overlay into this runtime.

Why retain the fallback?

Page inspection is structural estimation, not exact query evaluation. Failure must yield an estimate through a known route. The 5.3.2 fallback preserves its own index tie-break, rather than using the page walker’s different selection.

Operational escape hatch

-Dorg.eclipse.rdf4j.sail.lmdb.disablePageWalkingEstimator=true selects the complete old path when the store is opened. Configuration can also disable page cardinality estimation. Reopen after changing the property.

Existing sketch estimation is a separate maintenance option. The compatibility harness’s optimized modes and overlay callback evidence refer to the separate optimized binary; they do not establish accelerator execution in this branch.

12 / Bounded ingestion & recovery

Move work to disk
without changing its meaning.

Compatibility must survive a large legacy store and a long write transaction. Keeping every ID, alias or pending mutation in an unbounded heap collection would only relocate the failure.

Use spillable structures

A spill moves temporary transaction state from memory to disk. TxnRecordCache, PersistentSet and disk-backed semantic indexes bound resident working state while keeping pending operations replayable.

The MapDB-backed map fixes preserve lookup and initialization once the collection has crossed its spill boundary.

Resume native work safely

Index reconstruction works in bounded pieces with continuation keys. A map resize invalidates old native cursor state, so retry/reopen logic must use copied keys and managed transaction lifetimes.

Legacy write visibility relies on pending mutation state, not a complete context re-scan for each added statement.

Why this approach

Make resident state depend on the working batch, rather than the total repository or transaction.

Price we pay

Temporary disk use, native cursor/retry complexity, and more failure cleanup. “Bounded” does not mean constant total startup time or constant disk use.

Startup shortcut: the next ordinal is at least the maximum last ordinal in the dictionary and free-ID databases, plus one. For v6, a valid clean proof permits use of the persisted counter only when it reaches that endpoint; otherwise startup scans the dictionary. Reference-count recovery uses batches of 4,096. Cache replay copies at most 256 records and closes the native cursor before applying mutations. These bounds limit working memory, not total work.

The complexity tests assert operation-count and spill/growth contracts. They are not a fresh throughput benchmark or a promise that startup does no full validation scans.

Numeric equality is not term identity

-0.0 and +0.0 compare equally. An xsd:float literal promoted to double uses the rounded 32-bit float value. Neither correction authorizes replacing the stored lexical form.

15 / Deliberate limits & shortcuts

Preserve the store.
Accept the coordination cost.

The design minimizes representation changes on a maintenance line. These are the consequences a developer needs to keep in view.

DecisionWhy / benefitCost / limitation
New stores stay v2Keep maintenance creation compatible with the legacy representation.No automatic creation of v6 or migration tool in this branch.
Keep existing IDs and capability gatesA v6 store can return to the optimized runtime without mixed writer assumptions.Original inline config is required; unsupported formats/capabilities are refused.
Semantic alias index instead of rewritingRepair RDF matching while retaining legacy term bytes and references.Startup / disk work, alias-aware queries and writer lifetime complexity.
Pair readers and defer reclamationOld result IDs retain their original dictionary meaning.Reader slots and delayed reuse; leaked iterations hold resources longer.
Invalidate snapshots on resizeAvoid using unsafe native state after remapping.Retry required; uninterrupted snapshot survival remains outside the implemented contract.
Keep maintenance evaluatorConstrain the backport to storage compatibility and shared correctness.No optimized native evaluation, direct adjacency or value overlay.
Preserve unsupported learner stateRecognized stale artifacts are renamed before mutation rather than silently reused or overwritten.Preserved files accumulate; unknown schemas/artifacts block writes.

The maintenance learner helper validates the selected artifact set before moving recognized files to unique .maintenance-…preserved names. It does not make the optimized cost model usable here. Backup still needs coherent value/triple environments; this branch does not make two independent backups atomic.

Alternatives to revisit in a future design

Rewrite / migrate IDs: would simplify alias paths, but changes every owning index and undermines return-to-runtime compatibility. Backport the full optimized evaluator: would widen query and performance scope far beyond storage admission. Retain mapping generations across resize: could preserve held snapshots, but requires a coordinated native lifetime and paired-environment design. These are design alternatives inferred from the current boundaries, not implemented plans.

The extension boundary is persisted identity and owned lifetime. Optimizations may change execution; they must not silently change either contract.

16 / Where to start & extend

Read one contract.
Trace one complete lifetime.

Start at format resolution, then follow one statement from RDF term to ID to index and back through a dataset reader. Use the regression families to understand the boundaries before changing them.

  2. Use authentic producer fixtures. Match persisted inline/index configuration; retain original stores, hashes and negative admission cases.
  3. Cover the combinations that change representation. v2/v6, inline/dictionary, old/ordered numeric, explicit/inferred, alias/context/triple term, commit/rollback/reopen/growth.
  4. Keep source proof and runtime proof separate. Tests in the tree describe intended assertions. A current result needs the exact tested commit, binary and report provenance.
Small glossary for the source tour
SAIL
RDF4J’s storage abstraction. A repository can layer inferencing or validation above it.
Format / release
v2 and v6 describe persisted representations. 6.1.1 is an application release line.
Inline / dictionary ID
An inline ID contains a value encoding; a dictionary ID refers to stored term bytes.
Core reference / ordinal
A tagged literal reference can identify its core datatype. Its ordinal is the allocation sequence with type tags removed.
Reader / snapshot
A native read transaction pins a visible database generation. An RDF dataset needs both triples and values.
Epoch / retirement / GC
A runtime generation, a persisted wait state carrying removal revision, and eventual reclamation when safe.
Spill
Move temporary working state to a disk-backed structure while retaining its logical behavior.
Semantic alias
Different persisted IDs or spellings that represent the same RDF term under RDF equality.
Index order
spoc sorts subject, predicate, object, context. Configured orders determine useful query prefixes.
Fence
Persisted marker or native metadata that prevents an incompatible reader/writer from assuming the wrong representation.

### Prepared fresh-value and index import pipeline

This is a distinct ingestion path, not a claim that all dictionary writes happen on an asynchronous writer. `ValueStore.startFreshValueSessionIfEmpty()` creates import-local provisional IDs and reference deltas for an eligible empty-store import. `LmdbSailStore.storeFreshPreparedStatements()` assigns those IDs, fills bounded statement arrays, submits `PreparedImportOperation` work, and asks `TripleStore.prepareSecondaryIndexesAsync()` to prepare index keys on the index-preparation executor. In parallel with that index preparation, a `ValueStore.FreshValueEncoder` emits bounded record batches which the ingestion path passes to `ValueStore.persistPreparedValues()`. The caller retains these batches in `pendingFreshValueBatches`; commit publishes their cache/value state after the appropriate store commit path, while rollback removes provisional session state. The global-order import path has a corresponding `prepareGlobalIndexOrdersAsync()` branch.

Source anchors: `ValueStore.FreshValueSession`, `FreshValueAssignment`, `FreshValueEncoder`, `assignFreshValues()`, `persistPreparedValues()`, and `publishPreparedValues()` in [`ValueStore.java`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/ValueStore.java); `PreparedImportOperation`, `GlobalPreparedImportOperation`, `storeFreshPreparedStatements()`, and `pendingFreshValueBatches` in [`LmdbSailStore.java`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/LmdbSailStore.java); `prepareSecondaryIndexesAsync()` and `prepareGlobalIndexOrdersAsync()` in [`TripleStore.java`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/TripleStore.java). The completed [transaction guide section](storage-transactions-and-async-writes.md#async-prepared-statements-and-fresh-value-sessions) traces task cancellation, partial persistence, publication, and failure ordering from those call sites; it does not claim cross-environment atomicity.

### Compressed value-overlay subsystem (21 changed classes)

The `valueoverlay` package is a memory-only, leased lookup accelerator over exact value-store records. [`CompressedValueOverlay`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/valueoverlay/CompressedValueOverlay.java) states that it owns no RDF values and mints no dictionary IDs; absent entries, including reverse-index misses, remain unknown and must fall back to the authoritative store. [`ValueOverlayRegistry`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/valueoverlay/ValueOverlayRegistry.java) publishes an immutable base plus size-tiered changed-ID runs and retains snapshot views. It prepares a delta before native commit and completes publication only after commit succeeds and the transaction ID is verified. Builders/readers use record layouts/views/visitors, raw/front/token/vector page codecs, native slab allocation, and an admission budget; mutation deltas track deleted and reverse-visible IDs, and compaction can run asynchronously under configured caps.

All 21 changed paths in this subsystem are: `ByteArrayBuilder`, `ByteCursor`, `CompressedValueOverlay`, `FfmAccess`, `NativeLongList`, `NativeSlabAllocator`, `OverlayCapacityException`, `OverlayMemoryBudget`, `PackedVector`, `PageCodec`, `PhysicalRecord`, `RecordByteAccess`, `RecordFamily`, `TokenParse`, `ValueOverlayChanges`, `ValueOverlayDelta`, `ValueOverlayRegistry`, `ValueStoreRecordLayout`, `ValueStoreRecordView`, `ValueStoreRecordVisitor`, and `VectorPageCodec`. Relevant contract sources are `ValueStoreCompressedOverlayTest`, `ValueOverlayPageAccessTest`, and `CompressedValueOverlayOptionsTest`.

### Page-walking cardinality estimation

The two changed `estimate/**` classes are storage-owned because page reads are pinned to LMDB mapping/transaction lifetime; query docs cover estimator consumers. Production `TripleStore` borrows its already-open main database handle and a pinned read-only transaction. Its resize protocol increments a monotonically increasing mapping generation before any map-resize attempt, including failed/same-size attempts, and passes that generation into `LmdbPageCardinalityEstimator.readTransaction(txn, generation)`. The managed estimate scope must not outlive the transaction or permit resize/close. The compatibility constructor/path revalidates mapping discovery for each scope. The bounded `LmdbBtreeRangeCounter` decomposes a requested key range into exact boundary leaves and complete sibling subtrees, then measures exact small ranges or uses bounded structural samples with hard bounds. `TripleStore` falls back to the RDF4J 5.3.2 cursor estimator on disabled config, the `org.eclipse.rdf4j.sail.lmdb.disablePageWalkingEstimator` switch read at store construction, or an unexpected primary page-estimator failure; secondary-index failure preserves the primary estimate. See [overview: page-walking estimates](storage-overview.md#page-walking-cardinality-estimates), [`LmdbPageMappingLifecycleTest`](../../../core/sail/lmdb/src/test/java/org/eclipse/rdf4j/sail/lmdb/estimate/LmdbPageMappingLifecycleTest.java), and the [query estimate consumers](query-optimizer-and-statistics.md).

## Source checks resolved in the guides

* [Commit ordering and failure boundaries](storage-transactions-and-async-writes.md#ordinary-sail-transaction-sequence) confirm value LMDB commits before triple LMDB; there is no native cross-environment atomic rollback. Post-native-commit failure retains committed ID assignments, while derived adjacency gaps route back to authoritative statements.
* [Prepared writes and fresh-value sessions](storage-transactions-and-async-writes.md#async-prepared-statements-and-fresh-value-sessions) distinguish index-preparation worker work, bounded fresh-value record persistence, and optional value-overlay warm-up. Fresh prepared values persist on the ValueStore writer; they are not a general asynchronous dictionary commit.

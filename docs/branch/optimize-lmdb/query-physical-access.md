# Physical statement access and query sources

The query layer plans over an internal source contract rather than reaching into an LMDB cursor directly. That contract is where pattern IDs, ordered scans, reusable probes, prefix runs, root partitions, adjacency views, and query-local telemetry meet. A source capability only says that an operation may be attempted; it does not prove the corresponding view is present for this snapshot or that an operator will select it. The branch delta catalogued as Q5 covers query-side source adapters and access planning; persistent indexes, generation publication, and storage-owned cursor lifetimes are linked as unchanged or separately owned contracts rather than query-layer features.

## Source identity and composite datasets

[`NativeLmdbQuerySource`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/NativeLmdbQuerySource.java) provides the compiler with value-to-ID/value-from-ID operations, statement scans, optional ordered/prefix/range/triple-term access, probes, and optional adjacency/domain views. Native IDs may cross source wrappers only when `idSpace()` is the same object. Native compilation also checks `hasCanonicalIds()`: for a value store with non-canonical language tags, two term-equal language variants can have different IDs, so ID-only equality would not preserve generic value comparison.

`CompositeNativeLmdbQuerySource.combine` admits siblings only when they share the same ID-space object. It drops source branches proven empty for the selected dataset, preserves source order for ordinary concatenation, and merges per-source ordered iterators for an ordered request. If a single active source remains, the adapter delegates directly. Root partition plans are all-or-nothing: one member that cannot partition causes the composite to decline partitioning. Triple terms are scanned from one shared value dictionary, not concatenated over statement sources, because dictionary terms have value-space identity rather than statement-source multiplicity.

These query contracts borrow their read view and source lifetime from the store. See [storage transactions and async writes](storage-transactions-and-async-writes.md), [storage adjacency lifecycle](storage-adjacency-lifecycle.md), and [storage values and records](storage-values-and-records.md) for snapshot pinning, adjacency leases, and value lookup scopes.

## Statement scan arbitration

The LMDB implementation has two physical candidates for many unordered patterns: retained in-memory adjacency and the persistent statement index. [`LmdbStatementAccessArbiter`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/LmdbStatementAccessArbiter.java) is a fixed two-arm selector. It compares structural work intervals first; if a complete measured interval strictly beats the other lower bound, it can win. Otherwise adjacency is the conservative tie preference. A statement iterator is opened only after this choice is made.

Store-scoped primitive runtime evidence is partitioned by physical source, the four-position binding mask, requested order, ranged versus ordinary access, scan versus existence operation, and one of eight traversal kinds (probe, bound row, root, node-predicate, predicate sweep, ordered merge, spill sort, or native index). This prevents unrelated scan shapes from sharing a rate estimate. Before both arms have eight completed samples, overlapping estimates usually retain structural preference; after the preferred arm is warmed, a small bounded alternative sample can warm its rival. Once both are warm, the selector compares mean time-per-work and a two-standard-error radius, scaled by estimated work. A new store regime resets that key's primitive evidence. Censored/incomplete scans do not count as completed timings.

The observer distinguishes a candidate, an ineligible route, a selected source, and the iterator actually opened; scan-completion measurements are emitted when the measured iterator closes or exhausts. Consequently a plan explanation or advertised index is not itself proof that adjacency served rows. Runtime measurement can influence the physical source choice, but source capability, the direct-adjacency gates, requested order, binding shape, and current generation still constrain eligibility. Access telemetry/property details are in [runtime configuration](query-configuration.md) and [strategy explanation](query-arbitration-and-explanation.md).

## Repeated probes and bounded scans

`NativeProbe` is a cursor-owning reusable handle for repeated pattern lookups. An `open` iterator remains valid only until the next open or probe close. Implementations may therefore retain an LMDB cursor, reusable buffers, and the dataset stamp while repositioning to each key. A probe may expose a bounded exact adjacency view, key domain, node-predicate projection, wildcard adjacency, or node-domain synopsis. A `null` view means the complete requested stage cannot be served; it is not an empty result. The consumer must close borrowed views/cursors before or with the probe. Every worker uses its own probe/view because their cursors are mutable.

An optional [`LmdbKeyRange`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/LmdbKeyRange.java) narrows an LMDB-key interval only when an implementation can apply the range without dropping matches; otherwise the source contract falls back to the full pattern scan. A [`LmdbPrefixRunPlan`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/LmdbPrefixRunPlan.java) plus `prefixRuns` iterates distinct leading-key runs and their ranges. This can change work from visiting every tuple to visiting each useful run for grouping or duplicate elimination, but it is only valid when index order and prefix fields match the consumer's proof. The type of the plan is query-facing; storage documents how index order, run cursors, and range encoding are implemented.

For root scans, `planRootScanPartitions` may expose source-specific disjoint partitions. The composite asks every active source for the requested target and tags its partitions with stable member ordinals; a shared queue balances actual work. Parallel rows/aggregates still require their own operator, estimate, source-fork, cancellation, and memory admission gates. A root partition request is not equivalent to blindly splitting arbitrary key ranges.

## Adjacency views, domains, and predicate routes

Operators may request immutable, revision-valid borrowed views through a probe: one predicate/direction adjacency; exact node and presence domains; intersections; datatype summaries; node-to-predicate projections; dynamic adjacency; or wildcard-predicate adjacency. A complete view can enable membership, count, aggregate, path-seed, existence, or factorized access without decoding ordinary statement records. Each method has its own exact completeness requirement and refusal path. For example, a node-domain intersection returns `null` if either direction lacks a complete bounded synopsis; it does not silently intersect partial domains. Wildcard adjacency also requires one common visible snapshot across the predicate domain and every fixed-predicate plane.

[`LmdbNodePredicateRoute`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/LmdbNodePredicateRoute.java) selects a route for eligible node-predicate enumerations using a conservative modeled saving and byte-admission bound. The actual projection is supplied by storage and can be refused when the snapshot does not contain a complete representation. Root scan, direct adjacency bound probes, empty-pattern pruning, predicate projection serving, planner statistics, and adjacency aggregate shortcuts have distinct gates. Their on/off switches are listed in [query configuration](query-configuration.md); storage owns the structures, coverage certificates, and retained-memory budget.

The synopsis switch is especially easy to misread: disabling `rdf4j.lmdb.directAdjacency.synopsis.enabled` prevents building or consuming the optional retained `labelSynopsis`, `nodeDomainSynopsis`, and `nodeDomainPresence` query accessors. It does not disable the separate `nodeDomainIntersection()` accessor, nor remove intrinsic SOC/OSC plane, root, fiber, or multiplicity metadata. A retained synopsis is generation-scoped and borrowed only through its owning probe; never retain it in a reusable plan or compiler cache.

## Fallback and error boundaries

Physical alternatives are local. If a bound probe cannot be opened, the enclosing candidate may decline before output and another registered strategy can be attempted. If a source cannot honor a range safely, the source performs an ordinary scan. If a required complete adjacency or synopsis view is unavailable, an operator can use its explicitly implemented statement/index route or decline to a caller fallback. None of these rules permits restarting an already-published query from another source: a failure after output propagates while the selected iterator, probe, adjacency views, and reservations close.

Where exact encounter order matters, the source can request `statementsInEncounterOrder`; it must not replace that with another physical index order merely because the replacement contains the same rows. Ordered merge across composite inputs is a separate capability from unordered concatenation. Parallel partitioning is likewise declined when ordering, range, or source conditions are incompatible; sorted output is not inferred from a partitioned scan.

## Illustrative access walkthrough (source-only)

For a query with `?person <urn:email> ?mail` followed by a selective local `FILTER`, the statement pattern compiles to IDs and asks the source for a pattern iterator. It may choose a bound/index access or adjacency based on the pattern's bindings, order and range needs, source generation, and access costs. A later join proposal can try a batch or join family, each of which may own per-worker probes. If the source cannot offer a required synopsis, that route declines before returning rows; the ordinary statement route remains valid if the enclosing plan registered it. The generic/physical selection does not change SPARQL bag multiplicity or filter error behavior. This is a source-only access-path illustration, not an observed route or performance claim.

## Extension and test map

When adding a physical access capability, specify: the authority and snapshot token; exact completeness/order guarantees; whether the returned cursor or view is borrowed; who closes it; what `null` means; how range and binding arguments are interpreted; and what exact fallback remains. Add coverage for empty and multi-source composites, mismatched ID spaces, duplicate source rows, order and multiplicity, stale-generation refusal, close-on-open-failure, and one query cancellation path. Record the *selected/opened* access route rather than only advertising planning capability.

Useful source contracts include [`LmdbStatementAccessArbiterTest`](../../../core/sail/lmdb/src/test/java/org/eclipse/rdf4j/sail/lmdb/LmdbStatementAccessArbiterTest.java), [`LmdbDirectAdjacencyQueryTest`](../../../core/sail/lmdb/src/test/java/org/eclipse/rdf4j/sail/lmdb/LmdbDirectAdjacencyQueryTest.java), [`LmdbPrefixRunQueryTest`](../../../core/sail/lmdb/src/test/java/org/eclipse/rdf4j/sail/lmdb/LmdbPrefixRunQueryTest.java), and the root-scan contracts linked from [query test map](query-test-map.md).

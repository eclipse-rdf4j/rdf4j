# LMDB strategy arbitration and explanations

An explain decision is a report about one dispatch point, not a prediction that the whole query will run in one physical operator. This guide follows the offered candidate set through selection, opening, fallback, and explanation. The branch delta catalogued as Q10 covers the LMDB proposal, arbitration, and explanation paths; stable fallback behavior and generic evaluation remain the semantic baseline for these changes.

## Candidate admission, selection and opening

The row, ordered, and group dispatchers first try structural fast paths, then construct lazy [`LmdbNativeStrategyProposal`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/LmdbNativeStrategyProposal.java) objects. A proposer returns `null` if the current shape cannot use that family; this is a structural decline, not a loser in a cost comparison. For an offered candidate, its tag, work interval, startup work, estimated output and opener remain separate fields. Build/opening resources are deferred until the winning candidate is selected.

Without an adaptive source model, [`LmdbNativeStrategyArbiter`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/LmdbNativeStrategyArbiter.java) compares effective work intervals (including a finite consumer slice when available). It removes a candidate only if a rival's whole interval strictly beats it. Among the nondominated set it uses the stable specialization preference table, with a tag tie-break. This means an overlapping/unknown estimate leaves the stable policy in place; a midpoint is not enough to displace a strategy. If startup dominates a small LIMIT, the proposal can price only the rows the consumer may consume, rather than its full drain.

When a source-scoped adaptive model is present, the arbiter converts work to predicted elapsed time using measured strategy calibration when available, then asks the hierarchical cost model to compare prediction intervals. The model separates machine-wide, strategy-family/shape and exact-variant evidence so shared uncertainty can cancel in pairwise comparison. A measured variant's latest completed time for the relevant query shape replaces its smoothed center; completed and censored probe data have different update rules. Cost evidence displaces a stable incumbent only under the pairwise confidence test, not merely because one expected-time midpoint is smaller. Cold structural-only arms retain an ordinal basis until comparable features or timing evidence exist. See [cost learning and adaptation](query-cost-learning-and-adaptation.md).

Every selection rule operates only over the candidates that the actual dispatch site offered. An explanation's strategy catalog may list families that were declined or not relevant to this shape. A family appearing in the catalog, being forceable, passing compile-time recognition, and successfully opening are four different facts.

## Open decline, retry and forced strategy

After selection, `open()` may still return `null` if bind-time views, estimates, reservations, or source capabilities no longer satisfy the offer. The arbiter then removes that candidate, re-ranks the remaining set, and releases resources owned by non-winners. A proposal that fails while constructing itself must release reservations it has not transferred to the arbiter; a returned proposal's `close()` owns them. The winner's cursor/resources live with the consuming cursor/aggregate result.

Some dispatchers register a terminal semantic fallback outside the probeable set. It is used only after ordinary candidates decline/censor; adaptive trial must not consume the only valid execution route. Other sites, such as ORDER BY fusion, have an unconditional caller-level fallback and use optional forcing semantics so a forced family that is not applicable at that shortcut can still be tried at its later authoritative site.

Force controls bypass normal cost ranking only at the authoritative dispatch point. A mandatory forced family that was not offered or whose open returned `null` fails with a `QueryEvaluationException` naming the requested tag and captured decline reason; it does not quietly run `nestedLoop`. Forcing at an optional shortcut quietly declines if no candidate matches there, allowing the caller's own normal path to continue. Exact forceable families are defined by [`LmdbNativeForceableStrategies`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/LmdbNativeForceableStrategies.java) and the current family reachability notes in [strategy families](query-strategy-families.md).

Candidate open decline and post-open iteration failure are different. Before the first row is committed, a decision site may try an alternative if it has one and can safely close the attempted resources. After a row has escaped, restarting would risk duplicated/missing solutions and repeated volatile or remote work. Errors, cancellation, and failures then propagate through the selected cursor, with cleanup. A blocking open may materialize work before it returns the first row; that is still pre-output and only recoverable if the route reports a safe decline rather than a semantic/query error.

## Adaptive probes and hedges are opt-in policies

The adaptive policy can return one of four dispatch shapes: normal winner; bounded rival probe with incumbent fallback; a hedge that races both; or a guarded normal winner with a delayed backup. A dispatch point must explicitly register its trial drain/discard harness to be probe-safe, and shadow-context/backup support to hedge. Without those callbacks the policy does not guess how to discard output or duplicate an execution safely.

The probe policy reserves a deadline from the incumbent prediction, a per-query probe slot and a store-scoped safety-credit reservation before starting a rival. It uses a single-flight scheduler per physical variant/regime/epoch; cooldown, dormant-until-epoch, and quarantine state prevent repeated unsafe trials. Trial output is buffered/discarded and cannot escape as the query result. Completed trials train timing and feature ratios; a deadline censor contributes a right-censored latency bound but not incomplete feature counts. A query-wide probe cap limits cumulative latency overhead across many operators. These policies are gated independently; numeric tuning is documented in [configuration](query-configuration.md).

Hedging launches a second arm only where a shadow context, candidate cursor handoff and output exchange are available. A global bounded semaphore caps concurrent hedges; permits remain occupied until a losing arm actually exits, so an unresponsive cancellation degrades capacity rather than creating unlimited workers. Normal-dispatch guards require a measured, non-quarantined backup with enough evidence. Probe/hedge controls change runtime history and may run redundant work; defaults and exact eligibility live in [cost learning and adaptation](query-cost-learning-and-adaptation.md).

## Explain and telemetry boundary

`LmdbNativeExplain` and `LmdbNativeAttemptMetrics` record compile, proposal, decline, lowering, candidate-open and actual execution-path details through different events. Read the path actually emitted by a dispatch, not a static candidate list, as evidence that a physical operator ran. Preview invokes no opener, reserves no execution resources, and must not train the model; it records “execution-time binding and admission must still succeed” for candidates that could be selected. Query explanation output is therefore an eligibility/selection preview, not a runtime trace.

Normal dispatch logging includes evaluation/decision id, dispatch point, strategy tag, role and reason. Cost telemetry includes execution route and metrics used by the learning system; debug tracing is a separate direct system property and is not part of the boolean runtime allowlist. Server/Workbench exposure and explanation wire format are covered in [integration plan explanation and telemetry](integration-plan-explanation-and-telemetry.md).

## Illustrative control-flow example (source-only)

For a basic join with both `nestedLoop` and a batch proposal structurally available, candidate construction can report both. The initial choice follows strict interval dominance or, when intervals overlap, stable preference. If batch bind later declines before output because a required view could not be leased, the arbiter releases it and tries the remaining proposal. If instead batch emits a row and then encounters an I/O failure, the query reports that failure and closes the cursor; it does not start nested loop from the first row. An optimized explanation may show the candidate and the possible fallback but cannot guarantee the bind succeeded. This is a source-only control-flow illustration; actual candidate availability depends on the query and source.

# LMDB query memory and result lifecycle

Query memory is owned by several scopes. A source snapshot and adjacency generation have storage lifetimes; a native query row, reservations, worker queues, and cursor state have execution lifetimes; projected `BindingSet` values can outlive the cursor only after materialization/detachment. Treating all of these as one “query memory limit” would overstate what the implementation accounts. The branch delta catalogued as Q13 covers query-owned reservations, buffering, and result materialization; storage allocation and snapshot leases are described only as lifetime boundaries owned by the storage guides.

## Explicit query-memory accounting

[`LmdbQueryMemoryManager`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/LmdbQueryMemoryManager.java) is a process-wide authority with a synchronized global byte ledger and a per-query sub-ledger. The property `rdf4j.lmdb.queryMemory.maxBytes` is a positive byte count; absent or non-positive values use `max(1 GiB, Runtime.maxMemory()/2)`. `rdf4j.lmdb.queryMemory.perQueryMaxBytes` is also a positive byte count; its default is `max(1, globalLimit/4)` and it is clamped to the global limit. These values freeze when the process singleton is first initialized, not on every query.

Reservations are exact accounting claims supplied by an operator. A reserve/grow either succeeds immediately or refuses; it never waits for another query. On pressure, the manager selects the oldest registered reclaimable reservation (within the requesting query when its query cap is the limiting constraint) and calls `spill()` first, then `shed()`. If neither works, the reservation becomes non-reclaimable; if room still cannot be made, reserve returns `null` and the operator chooses its exact fallback or decline path. Closing a reservation releases its claim; closing a ledger releases every remaining claim and is idempotent.

One [`LmdbNativeQueryMemoryScope`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/LmdbNativeQueryMemoryScope.java) is shared by the root `RowState` and derived rows, including worker/scratch rows, so a single query does not get a fresh per-query cap per join build. Operators that reserve memory include hash builds, distinct/group state, morsel queues, node-domain synopses, factor/prefix memo batches and packed-tree group output. The exact reservation is chosen by each operator; the manager does not estimate arbitrary object graphs.

The limits therefore bound only structures that explicitly reserve their memory. They are not a JVM heap cap, do not automatically include every `BindingSet`/memo/list, and do not account for data held by the storage generation or persistent mapping. A row or island replay buffer can still grow with output cardinality unless that owner has its own bound. See [joins and factors](query-joins-and-factors.md), [strategy families](query-strategy-families.md), and [storage adjacency lifecycle](storage-adjacency-lifecycle.md) for their distinct memory owners.

## Row representations and value boundaries

The native execution row holds ids in primitive slots plus masks for bound/assured positions. Projection metadata copies selected ids into a [`NativeProjectedBindingSet`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/NativeProjectedBindingSet.java). With `rdf4j.lmdb.nativeLazyResults.enabled=true` (default), values are looked up lazily when a caller asks for a binding. A row retains the query source authority until detached; it is not safe to promise such a row remains source-independent while it still has uninitialized values.

At the Sail boundary, [`LmdbValueMaterializingIteration`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/LmdbValueMaterializingIteration.java) materializes the first result before returning it. Later results are gathered in a growing batch (initial capacity 128, doubling up to a default 4,096 rows), their known lazy values are deduplicated/grouped by value-store revision and initialized in value-id order, then native projected rows are detached from the source. The first row is a single-row path; subsequent batch work amortizes repeated dictionary initialization. The value batch is not governed by the query-memory ledger in this implementation; value IDs/records and resolution authority are described in [storage values and records](storage-values-and-records.md).

`NativeProjectedBindingSet.materializeAndDetach()` resolves the bound values and clears its source reference. `getValue()` can still lazily resolve an individual value before that point; after detachment every bound value must already be available. The public iterator/boundary determines when this wrapper runs. Storage documents persistent value authority, revisions, and lazy value records in [storage values and records](storage-values-and-records.md) and overlays in [storage value overlay](storage-value-overlay.md).

## Cursor and worker ownership

Native plan objects describe execution shape. Per-open bind state, scanners, adjacency probe views, kernel instances, row buffers, and worker tasks belong to the opened cursor/aggregate scope. A strategy proposal may own an unpublished reservation; if proposal construction throws before it is returned, its proposer releases it. Once returned, the arbiter releases losers promptly after one winner opens. A selected cursor owns the winner's resources until exhaustion, close, cancellation, or exception.

Close must cascade through the result wrapper to its input cursor, close native scanner/probe/adjacency leases, cancel or drain worker tasks where that execution family requires it, and release memory reservations. Snapshot/generation leases are separate: storage code owns their retention and release, and a query cannot hold an adjacency cursor past the source's snapshot contract. Inspect operator-specific close paths before adding another buffer or asynchronous continuation.

## Cancellation and first-result boundary

[`NativeCancellationToken`](../../../core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/NativeCancellationToken.java) observes explicit cancellation, interruption of the evaluation-creating thread, interruption of a worker, and an optional parent token. Parallel pipelines may create a child token so a failed/trial pipeline can stop its workers without cancelling a separate fallback or the enclosing evaluation. Generated kernels poll through `KernelCancellation`; interpreters/cursors poll at their own operator boundaries. Cancellation responsiveness is therefore determined by that route's poll points, not guaranteed between every two low-level index records.

Before first output, an opener/preflight can decline and an arbiter may release resources and try a remaining candidate, when that decision site registered one. A blocking operator can do substantial work before its first row (sort, hash build, group materialization, complete general-path endpoint set); this does not mean a second route may safely start after publication. Once a row has escaped, errors/cancellation close the chosen route and propagate. Restarting a whole plan after output could duplicate or omit solutions, repeat volatile expression calls, remote SERVICE effects, or bind-time work. See [routing and hosts](query-routing-and-hosts.md#what-a-runtime-fallback-can-and-cannot-do) and [strategy arbitration](query-arbitration-and-explanation.md).

## Retained structures to review

| Structure | Owner/lifetime | Bound or fallback contract |
|---|---|---|
| Process compiled-kernel classes | Static Janino or batch-specialization LRU. | Entry and generated-byte caps are documented in [IR/codegen](query-ir-and-codegen.md); this is class-cache memory, separate from per-query reservations. |
| Island materialization/replay rows | Per evaluation or per LATERAL entry frame. | Keyed mode admits at most 256 distinct keys; this does not bound row count/bytes. Source and scope in [routing](query-routing-and-hosts.md). |
| Factorized branch/value memo | One factorized sink's shared `MemoBudget`. | Entry and value caps; on overflow bypasses caching/re-scans rather than losing solutions. |
| Factorized prefix batch | Per query row plan/prefix depth. | Bounded by cumulative memo budget and array-capacity guards; cache-backed probes can suppress duplicate local memoization. |
| `OPTIONAL` hash/memo/sweep | One compiled/open left-join plan. | Each strategy uses separate row/key thresholds and shape gates. No one configured row limit is a byte limit. |
| General path endpoint set | One path evaluation frame. | Deduplicated endpoint-pair materialization precedes first output; key set can scale with reachable pairs. Specialized paths have bounded target/memo caches. |
| Sort/top-K/group state | One ordering or aggregate execution. | Top-K bounds retained candidates only when its semantic/capacity checks admit; otherwise full sort/group storage and explicit reservations apply. |
| Sail materialization batch | Result adapter until rows are detached. | Row count grows to configured/default maximum batch; not a native query-ledger reservation. |

Exact ceilings and their configuration are listed in [query configuration](query-configuration.md). “Bounded” describes only the specific entry/value/byte dimension in that table; it must not be restated as a universal bound on all rows or bytes.

## Extension checklist and source contracts

For a new operator, identify every retained array/map/list, its worst-case cardinality, whether it is query-, cursor-, source-, or process-owned, and whether its bytes are reserved. Define what happens when admission refuses (stream, spill, exact fallback, or decline). Close scanner/lease and task ownership on normal completion, cancellation, failure and losing-candidate paths. For result rows, state whether values are lazy and who detaches them from the storage source.

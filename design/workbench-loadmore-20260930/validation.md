## Measured transport decision

The codec report is `/tmp/rdf4j7-workbench-loadmore-20260930/codec-format-report.md`. It uses actual tuple/graph term streams, shared and unique long literals, repeated shuffled encoder samples, lossless decoder checks and paired normalized parse samples on the recorded macOS/Java/Node environment.

Compact array terms reduce **raw UTF-8 about 40%** and normalized parsing time about **42%** for ordinary tuple/graph terms. At the same 32-row cadence, zstd compressed output changes only about **0.7%**. Independently, increasing steady records to 1,024 rows reduces zstd output by about **24%** in the ordinary tuple corpus. Long-literal parsing has no material array improvement. Negative zstd levels encode slightly faster in some samples but produce materially larger output; zstd level 1 is the measured combined delivery choice, not a universally fastest or raw-encoder-fastest codec.

The chosen query-only cadence is first up to 32 rows, then up to 1,024, with an exact 256 KiB encoded-record cap and a lossless oversized single-row exception. At one million ordinary rows this predicts 978 storage callbacks instead of 31,250 before byte-cap effects. That count is derived from framing, not an observed production million-row result.

Twenty-four gzip/HTTP-deflate level 1 comparisons use two warmups and seven shuffled samples. Deflate saves exactly the 12-byte wrapper difference per response and has higher measured encode/decode medians. Gzip remains the measured fallback. Supported alternatives include Brotli quality 0 and zstd negative levels; all retained comparison payloads round-trip exactly. Existing dependency versions are unchanged.

The native unfinished-frame gate passes **156/156** cases: Chromium 60/60, Firefox 60/60 and WebKit 36/36. Native request headers advertise gzip/deflate/br/zstd in Chromium and Firefox, and gzip/deflate in WebKit. No JavaScript Accept-Encoding override is used. Every supported case matches decoded SHA-256, bytes, rows and record counts; first records parse before browser ACK, server continuation and response completion. The loopback probe proves browser decoding/progress and representation equality, rather than servlet or IndexedDB throughput.

Across the same 53.83 MiB raw native corpus per available coding/browser, zstd totals 7.12 MiB, gzip/deflate 20.62 MiB and Brotli 20.97 MiB. Median loopback read/decode is roughly 13–14 ms in Chromium, 16–18 ms in Firefox and 18 ms in WebKit; first-prefix ACK is 1.6–3 ms. These values are capability measurements only. The zstd encoder constrains its HTTP frame window to 8 MiB and the decoder proof enforces that bound.

Root reviewed the consolidated report and native artifact, then approved query-only v2, bounded hybrid cadence, q-aware zstd level 1 and gzip level 1 fallback. Production regression tests still precede each promoted behavior. Downloads, generic page models and the separate Server compression defaults retain their legacy boundaries.

## Million-row boundary

The first object/v1/identity attempt requested the correct default batch of 1,000,000 at offset zero, without legacy limit_query. It received 292,657 partial rows and displayed query timeout. The preserved snapshot has 17 mounted data rows, 18 table rows including a spacer, 201 result elements and server RSS 551,136–556,384 KiB (about 538–543 MiB). Snapshot heap is not peak heap.

The scratch harness incorrectly waited for a grouped success label and did not terminate on a settled error. Its 900-second wait therefore is **not a measured production completion or server timeout duration**. That failed run did not capture network finish, terminal receipt or storage drain, and it did not complete the million-row or reexecution-disposal acceptance. Evidence is `million-baseline-v1/measurement.json` and `run.log`; preserve it as partial/default-timeout evidence.

The first pre-full-query, offset-protocol timeout-zero run used a 1,001,000-row product. It loaded exactly 1,000,000 rows, with a 79.5 ms first rendered row, 17 mounted data rows and 191 result elements. CDP main-thread heap was about 9 MiB; that snapshot is not peak heap across workers. Request finish can include consumption backpressure, so neither number is attributed to server CPU.

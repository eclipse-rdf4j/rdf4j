## Measurement record and limits

### Actual Worker / IndexedDB complexity probe

On generation `20260930-053657`, a network-free Chromium probe used the public `createRowStore()` API and real served Worker/IndexedDB, appending representative two-term rows in 1,024-row calls. It issued no SPARQL query. A test-only response wrapper counted IndexedDB methods and timed the existing worker function without changing its control flow. Both owned stores preserved exact first/middle/last samples and were absent from metadata and row storage after awaited disposal.

| ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 10,000 | 10 | 241 ms (25.5/39.8 ms) | 237 ms | 3.0 ms | 0.8 ms | 941 ms | 10,000 `rows.add`; 10,000 cursor deletes/continues |
| 100,000 | 98 | 20.43 s (216/370 ms) | 20.39 s | 25.1 ms | 0.7 ms | 15.91 s | 100,000 `rows.add`; 100,000 cursor deletes/continues |

Each append transaction did one metadata `get`, one `rows.add` per input row, and one metadata `put`. Disposal used one cursor and issued one delete and continuation per row. Count and one-row sample reads were sub-millisecond. This directly isolates the delay from network, parser, and result DOM work: the worker transaction dominates; main-thread clone and construction are negligible by comparison. Chromium reported no long tasks and a maximum sampled event-loop gap of 2.5 ms; CDP page heap was about 3.99 MB after 100k rows, browser process-family RSS about 424 MB, and preview RSS stayed near 882.5 MB. These process-level memory figures are not per-page heap.

## Final full-query and mobile-anchor acceptance

The timeout-zero query `SELECT ?s ?p ?o WHERE { VALUES ?s { ... } VALUES ?p { ... } VALUES ?o { ... } }` produced exactly 1,201,000 results on generation `20260930-123738`. The first request kept the original query unchanged, used `batch-size=1000000` and `batch-offset=0`, streamed exactly one million rows, then drained the same evaluation. It reported progress at 1.1m and 1.2m and only published exact total/time at completion. Load more sent the same frozen query with `batch-offset=1000000`; it skipped the prior prefix locally and appended only the remaining 201,000 rows to the same result-store owner. First/middle/final access in Table and Records caused no extra query request. Main and saved final screenshots, progress/complete/append/reset snapshots, native zstd response headers, encoded/decoded bytes, and store-owner timings are in `/tmp/rdf4j7-workbench-loadmore-20260930/full-query-reset-table-20260930-140121/`; saved-result full-query evidence is in `saved-large-query-20260930-141049/`. The worker heap was not sampled; values are snapshots, not peaks.

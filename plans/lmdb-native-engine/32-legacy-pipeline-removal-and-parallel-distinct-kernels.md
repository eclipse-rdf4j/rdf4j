Predecessors incorporated by reference: `plans/lmdb-native-engine/17-janino-whole-stage-codegen.md` (the legacy pipeline being removed), `plans/lmdb-native-engine/19-kernel-ir-primitives.md` and `20-kernel-lowering-row.md` (the IR kernel tier that replaces it), `plans/lmdb-native-engine/31-parallel-kernel-parity.md` (the parallel rung this plan extends).

## Purpose / Big Picture

The LMDB "native engine" in `core/sail/lmdb` evaluates SPARQL queries through a ladder of execution strategies. Two of those strategies compile queries into runtime-generated Java (via the Janino embedded compiler): an old, shape-specific "whole-stage pipeline" (`core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/LmdbNativeJaninoPipeline.java`, from plan 17 milestone M3) and the newer, general IR kernel tier (`LmdbNativeKernelLowering` lowers a plan to a small intermediate representation, `LmdbNativeKernelEmitter` generates Java source, `LmdbNativeKernelExecution` runs it, `LmdbNativeParallelKernelRows` runs it morsel-parallel).

The legacy pipeline is now strictly worse than everything it preempts, and it sits FIRST in the kernel rung (`LmdbNativeRowStep.openKernelInput`, line ~950), so a plain basic graph pattern (BGP) of 2–6 constant-predicate patterns is absorbed by it before the IR kernel — or any parallel tier — can see the query. Its defects, all verified in this session: it materializes the entire result set eagerly before emitting the first row; its closing-edge steps are linear scans; it is strictly single-threaded with no parallel rung at all; and its admission is shape-based with a fictional cost signal (opens x 4096). A user-reported 10x regression on the SP2B-style query below is caused by exactly this: the interpreted adjacency path runs it on multiple workers, the legacy pipeline serializes it.

    PREFIX rdf:   <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
    PREFIX foaf:  <http://xmlns.com/foaf/0.1/>
    PREFIX bench: <http://localhost/vocabulary/bench/>
    PREFIX dc:    <http://purl.org/dc/elements/1.1/>
    SELECT DISTINCT ?person ?name
    WHERE {
      ?article rdf:type bench:Article .
      ?article dc:creator ?person .
      ?inproc rdf:type bench:Inproceedings .
      ?inproc dc:creator ?person .
      ?person foaf:name ?name
    }

After this plan: (1) the legacy pipeline is gone and plain BGP chains flow to the IR kernel tier; (2) the IR parallel rows rung can partition kernels whose root is a constant-key probe (the `?x rdf:type <Class>` root shape — today it declines `root-not-partitionable` because only `EnumerateAdjKeys`/`EnumerateDomain` roots partition); (3) DISTINCT-on-N-variables queries over simple BGPs sink their DISTINCT into the kernel with order-aware dedup that exploits the sorted adjacency data instead of hashing every row.

Observable outcome: with `-Drdf4j.lmdb.janinoCodegen.debug=true` and a store containing the SP2B-style data, the query above runs through `irKernelParallel` (`LmdbNativeParallelKernelRows.PARALLEL_RUNS` increments), returns identical results to the interpreted engine, and no code path references `LmdbNativeJaninoPipeline` anymore.

## Milestone 2 — Parallel kernels for constant-key roots

Scope: the parallel rows rung (`LmdbNativeParallelKernelRows.tryOpen`) partitions only pipelines rooted at `EnumerateAdjKeys` (key-ordinal windows via the `KeyWindowView` decorator) or `EnumerateDomain` (array slices). A BGP whose cheapest first pattern is `?x <p> <const>` (or `<const> <p> ?x`) lowers its root to `Probe(adjacency, key=CONST-or-ENTRY, valueCol)` (`LmdbNativeKernelLowering.lowerPattern`, the `object != null && subject == null` arm at ~line 1150) — a single sorted neighbor run — and today declines `root-not-partitionable`, so exactly the `?article rdf:type bench:Article`-rooted family never parallelizes in the kernel tier even though the interpreted engine runs it on workers.

Revision note (2026-08-06, during implementation): the design below was NOT built. Lowering already intercepts pure-constant-key patterns ahead of the `Probe` arm and materializes the run as an ordered `EnumerateDomain` (see Surprises), which the existing domain-slice partitioning serves. The milestone's deliverable became the acceptance test plus the M3 unblocking; the decorator design is preserved below only in case entry-correlated root probes ever need it.

Original design (unbuilt): partition the RUN, not the key domain. A new decorator `RunWindowView` in `LmdbNativeKernelPartitions` wraps the root's adjacency view and exposes only run positions `[from, to)`: `find` delegates (workers share the query snapshot via `openParallelSources`, so the handle and run length are identical); `size(h)` returns `min(size, to) - from` clamped at 0; `neighborAt/contextAt/copyNeighbors/copyContexts` offset by `from` and clamp lengths; `lowerBound` offsets both ways. This is sound because lowering allocates a FRESH adjacency index per node (`Builder.adjacency` at line ~586 appends unconditionally, no sharing), and a defensive `Requirements`-walk still verifies no other pipeline node references the root's index. The generated code is untouched — same shape key, same compile cache, exactly the `KeyWindowView` playbook. A new `partitionableRootProbe(pipeline)` returns the adjacency index when position 0 is a `Probe` whose key operand is CONST or ENTRY (a COLUMN key cannot occur at position 0) and no later node uses that index; `tryOpen` computes `rootKeys` as the run length (`find` + `size`, 0 when the run is absent — then parallelism is pointless and the sequential kernel serves) and reuses the existing `ranges`/work-stealing/window-install machinery, installing `RunWindowView` instead of `KeyWindowView` for this root kind.

Validation: new test in `LmdbNativeIrKernelParallelTest` — a BGP rooted at a constant-object type pattern over enough rows to clear `root-too-small`, asserting `PARALLEL_RUNS` increments and results match the interpreted engine. Red first (current code declines `root-not-partitionable`), then green.

## Milestone 3 — DISTINCT sinking with order-aware dedup

Scope: `SELECT DISTINCT ?a ?b ... WHERE { <simple BGP> }`. Today the kernel emits every produced column and the engine dedups above it; the emitter's `Emit.distinct` machinery (per-kernel `RowSet` dedup) and the parallel consumer's cross-window dedup (plan 31 M4) exist but are dormant because lowering never sets `distinct=true` (all three `Emit` construction sites pass `false`).

Design, in three tiers that exploit the data order rather than hashing blindly:

1. Projection pushdown. `LmdbNativeRowStep` knows the consumer's DISTINCT (`distinct` field) and the retained slots (`sourceSlots`/`sortLayout.liveToPlan`). Pass both into `LmdbNativeKernelExecution.tryOpenRows` → lowering. When every retained slot is a produced column, no residual filter reads a non-retained produced slot (residuals run on the consumer's `RowState` against bound columns — check their masks), and no OPTIONAL null-arm subtleties apply (first increment: decline sinking when `LeftProbe`/`LeftGroup`/`Union`/`PathExpand` present), emit ONLY the retained columns and set `Emit.distinct=true`. This alone shrinks the result surface — the measured cap on row-materializing kernels (plan 17: ~127k-row RowState/BindingSet pumping ate the 10.2x ceiling down to 4.7x).
2. Ordered dedup in the emitter. Nested loops over sorted producers emit rows in lexicographic order of the columns taken in loop-depth order, PROVIDED each producer is sorted: `EnumerateAdjKeys` key columns are ascending (sorted key domain), `Probe`/`EnumerateAdjKeys` value columns are neighbor-ordered when `runsNeighborOrdered()` (context duplicates of a neighbor are adjacent), `EnumerateDomain` only if the domain is known sorted (VALUES is not — treat as unsorted). Compute the longest prefix of the emitted distinct columns (ordered by producing depth) that is "order-aligned": each successive column's producer strictly nested in the previous with no intervening skipped loop column. Dedup then becomes: (a) transition check on the aligned prefix (compare with the previously emitted prefix — equal prefix and no unaligned tail means duplicate; prefix advance resets); (b) for the unaligned tail, a per-prefix-group `RowSet` that is CLEARED on every prefix transition — bounded by the widest group instead of the whole result, cache-resident in the common case. When the whole distinct key is aligned (e.g. person-major plans: root key ?person, nested sorted run ?name), tier (b) vanishes and dedup is two comparisons per row with zero allocations.
3. Parallel disjoint windows. When the leading aligned distinct column is the partition column (`EnumerateAdjKeys` key windows, or M2 run windows whose value column leads the distinct key), windows produce disjoint leading values, so the consumer's cross-window `HashSet<PackedKey>` dedup is unnecessary — skip it. Otherwise keep it (correct today, just not free). The acceptance query's article-major plan keeps consumer dedup; a future person-major plan (M4) gets the free version.

Validation: emitter-level tests for the aligned-prefix computation and both dedup tiers (the existing `LmdbNativeKernelIrEmitterTest` style: synthetic adjacency fixtures, exact expected rows); an end-to-end test asserting a DISTINCT BGP query engages the kernel with `Emit.distinct` set (observable via the debug shape-key print or a bridge) and matches interpreted results; the differential fuzz DISTINCT rounds (already generated: `SELECT DISTINCT *` variants in `janinoKernelBasicGraphPatterns`) stay green.

## Milestone 4 — Existential rewrite of projected-away branches (implemented on user instruction)

Under DISTINCT, a join branch whose fresh variables are all projected away contributes only existence (the factorized tier's `ROLE_EXISTS`). In IR terms: `?article rdf:type bench:Article . ?article dc:creator ?person` with `?article` unretained lowers as `Exists` over a two-node sub-pipeline anchored on `?person`, leaving a spine (here `?person foaf:name ?name`) whose root enumeration makes the WHOLE distinct key order-aligned — dedup becomes two comparisons per row with zero hash state, and the parallel windows partition the leading key. Implementation: `existentialComponents` + `lowerExistentialComponent` in the lowering `Builder` (see Progress for the eligibility rules), reusing the aggregate rung's witness machinery for the sub-pipelines, active only when `lowerDistinctRows` set the retained mask. Join-order interplay is conservative: the spine keeps the derived order; components attach after it.

## Surprises & Discoveries

- Observation: lowering allocates a fresh adjacency index per IR node (`Builder.adjacency` appends a new `AdjacencyRequest` unconditionally), so root-view windowing can never corrupt a sibling node through a shared view.
- Observation (M1): `LmdbNativeQueryExplanationTest`'s telemetry test hardcodes `nativeExecutionPath=janinoKernel` — the legacy pipeline was load-bearing in one explain test only; every other engagement surface already tracks the IR rung separately (`KernelExecutionTestAccess`).
- Observation (M2): the planned `RunWindowView` (run-range windows for constant-key `Probe` roots) turned out to be unnecessary for the acceptance shape — `lowerPatternInline` already intercepts pure-constant-key patterns BEFORE the `Probe` arm and lowers them as run-materialized `EnumerateDomain`, which the parallel rung partitions by array slices. A root `Probe` only remains for entry-correlated keys, which the rung declines as `correlated-entry` anyway.
  Evidence: `LmdbNativeKernelLowering.lowerPatternInline`, the two `DomainRequest(pattern.p.constant, ..., bySubject)` arms with `markOrderedDomain`.
- Observation (M2/M3, the real blocker): DISTINCT queries with an ordered dedup strategy never reach `openUnorderedInput` at all — `LmdbNativeRowStep.initialize` opens `distinctPlan.arg.open(row)` directly (`PATH_ORDERED_DISTINCT`), a serial nested-loop cursor, bypassing kernels, batch, chunk, AND both parallel engines. Only the `GLOBAL_HASH` strategy fell through to the fast tiers. So the engine already had order-aware DISTINCT semantics (`NativeDistinctStrategy.ADJACENT`/`PARTITIONED_HASH` + `NativeOrderedDistinctTracker` — the interpreted twin of this plan's aligned/scoped tiers); what it lacked was a fast executor under them. That inverted M3's design: instead of teaching the kernel the planner's order, the kernel derives its own aligned prefix from its own loop structure and owns the whole dedup.
  Evidence: the acceptance test's red run — parity green for 300 rounds yet `PARALLEL_RUNS == 0` with zero `[ir-kernel-parallel]` decline output, meaning the rung was never consulted.
- Observation (M4): the aggregate rung's witness machinery (`lowerWitnessPatternPlan`, `witnessOperand`, greedy correlation) composes directly with row-side DISTINCT sinking; the only latent gap was `build()` sizing the kernel's columns without `scratchColumns`, which had been unreachable on the row rung until Exists rewrites appeared there.
- Observation (M3, caught by the full-module sweep, first version was WRONG): a sorted producer column may REPEAT a value — neighbor runs carry one entry per context — and a repeated value re-runs every deeper loop, so equal longer prefixes stop being adjacent and transition dedup misses them. The differential fuzz round `irKernelBasicGraphPatterns` produced four duplicate rows on `SELECT DISTINCT * WHERE { VALUES ?v0 {...} ?v0 p2 ?v1 . ?v1 p2 ?v2 . ?v2 p5 ?v3 . ?v3 p1 ?v4 }` over a store with a duplicate multi-context edge at the ?v3 level. Fix: only provably unique-and-sorted columns (a view's key domain) may CONTINUE the aligned chain; sorted-but-duplicable columns (probe values, expanded key-enumeration values, materialized run domains) are admissible only as the LAST aligned column. Note the composition stays sound: residual columns BELOW a duplicable terminal aligned column dedup correctly, because the repeated value's groups are consecutive so the scoped set is not cleared between them.
  Evidence: surefire failure "the following elements were unexpected: [(s2, s3, s13, s12, ...x4)]" pre-fix; same selection green post-fix.
- Observation (M3, caught by the full-module sweep): sink-attempt refusals recorded through the ordinary `decline()` helper registered as `PATH_IR_KERNEL` capability declines and broke `LmdbNativeKernelDeclineCensusTest` (4 pairs, all `distinct-sink:optional`) — even though the plain kernel served those queries right afterwards through `openUnorderedInput`. The sinking attempt is an EXTRA opportunity, not the kernel's verdict; all its refusals now go through a quiet, debug-only variant.
  Evidence: `target/kernel-decline-census.txt` pre-fix (`4 irKernel:distinct-sink:optional`); census test 3/3 green post-fix (506 s).

- Observation (M4, reported from the user's SP2B store, hotfixed same day): the existential rewrite made the acceptance query TIME OUT (60 s+, vs 60 ms interpreted; profile 100% in the paged-CSF per-ordinal reader `CompactCsfPageReader.pairAtOrdinal`). Root cause: `witnessPatternCorrelated` counts a CONSTANT endpoint as correlation, so when the class pattern preceded the creator pattern in the derived order, the witness lowered the class pattern first — enumerating the entire class extent inside the Exists, per outer row, through unmaterialized (>8192-edge) CSF runs read element by element. Fix: witness ordering prefers VARIABLE correlation (`witnessVariableCorrelated`); constants qualify only as a last resort. With it, the witness probes the person's small incoming creator run and closes the type with a seek. A dump-based structural test (`existentialWitnessesProbeFromVariableAnchorsNotConstants`) pins "no `find(c` in generated witnesses"; note its red/green is imperfect — the local fixture's derived order already had the creator pattern first, so the old code passed it too; the SP2B cardinalities that flip the derived order are what triggered the bug in production. The same trivial-constant-correlation pattern exists in the pre-existing `lowerWitnessJoin` (EXISTS/MINUS witnesses) and should get the same treatment (added to M5).
  Evidence: user profile report; post-fix parallel class 7/7 green, both kernel fuzz rounds green.

## Decision Log

- Decision: remove the legacy pipeline outright instead of demoting or default-off gating it.
  Rationale: every shape it recognizes is lowerable by the IR tier (plan 20 accepts plain `MultiJoinPlan` chains); it has no parallel rung and eager materialization by design; keeping two codegen rungs doubles the admission-regression surface (the user's 10x case). The IR tier's own admission threshold still gates codegen entry.
  Date/Author: 2026-08-06 / Claude (user instruction "try removing the legacy janino pipeline").
- Decision: keep the test bridge class name `JaninoPipelineTestAccess` while retargeting it to the IR counters.
  Rationale: eight test/benchmark files import it; the methods' meaning ("did a generated kernel engage") is unchanged. A rename is cosmetic churn in a plan that already touches the same files for real reasons.
  Date/Author: 2026-08-06 / Claude.
- Decision: drop the planned `RunWindowView` — no production change for root partitioning.
  Rationale: discovery above; the constant-key root already lowers to a partitionable, ordered domain. Building a second partition surface for a shape the rung cannot receive would be dead code.
  Date/Author: 2026-08-06 / Claude (supersedes the earlier decorator plan in this session).
- Decision: the DISTINCT-sunk kernel attempt sits AFTER the prefix-run tier and BEFORE the ordered-distinct serial branch; on success it owns the whole dedup (`distinctHandledByCursor = true`).
  Rationale: prefix-run is an established parallel tier with its own wins (ANALYTICS plan 15) — do not steal from it; the ordered-distinct branch is the serial bottleneck being replaced; consumer-side re-dedup would hide kernel dedup bugs, whereas owning it makes the differential fuzz rounds a direct oracle.
  Date/Author: 2026-08-06 / Claude.
- Decision: under sinking, multiplicity `ProbeClose` nodes demote to semi, and M4's rewrite targets whole scratch-variable components rather than single patterns.
  Rationale: a DISTINCT consumer cannot observe multiplicity, semi keeps emission grouped for the aligned tier, and component granularity is what makes the SP2B shape's `{ ?article a A . ?article creator ?person }` pair one Exists instead of two half-measures.
  Date/Author: 2026-08-06 / Claude (user: "add the rewrite of projected-away join branches as Exists semijoins under DISTINCT").
- Decision: aligned dedup carries a bind-time promise check (`alignedInputsOrdered`: every view `runsNeighborOrdered`, every domain unsigned-ascending) instead of trusting the lowering's static claim.
  Rationale: sortedness is a property of the store's view implementation, not of the plan shape; the M4-aggregate kernel set this precedent with `runsNeighborOrdered`. A failed check declines to the ladder — never runs a wrong kernel.
  Date/Author: 2026-08-06 / Claude (user: "order matters — take advantage of the order of the data when deduping").
- Decision: M3 dedups via ordered-transition tiers with a scoped, prefix-reset set for the unaligned tail, not a single global hash set.
  Rationale: user instruction "order matters — take advantage of the order of the data when deduping"; adjacency key domains and neighbor runs are sorted, so the aligned prefix dedups with comparisons, and the scoped set is bounded by group width instead of result size.
  Date/Author: 2026-08-06 / Claude.

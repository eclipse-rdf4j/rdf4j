This is a living ExecPlan maintained according to `.agent/PLANS.md`. Its Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective sections must remain current. ## Purpose / Big Picture


Execute sends the user's original SPARQL query unchanged, streams the first 1,000,000 results, then keeps evaluating and draining that same query to exhaustion so it can report the exact total and complete elapsed time. While draining beyond the first million, it reports monotonically increasing row/time progress every additional 100,000 rows or 3 seconds, including when waiting for the next result. The browser stores only the streamed results and lets the user browse them locally. A Load more action reruns the same frozen query unchanged and skips already loaded results locally before appending new ones. Workbench must not add LIMIT or OFFSET to query text. Query-result Next, Previous, page-size, and record-page controls disappear; unrelated repository/resource-list paging retains its behavior.

The implementation must preserve query semantics, typed RDF values, cancellation, accessibility, and responsive layout. A million rows must not mean a million elements or a million-row array retained on the browser's main thread. Transport compression and any stream-format change are selected from measurements of supported alternatives, rather than claims of a universally fastest codec.

## Surprises & Discoveries


The user now requires the initial execution to drain the full original query after streaming the first million rows, so exact totals and full elapsed time must come from the same evaluation rather than a synthetic LIMIT/OFFSET slice or an extra count query. During that drain, progress must advance by row count or elapsed time even when evaluation waits for its next item. QueryResultRenderer has a worker-owned IndexedDB row store and bounded rendered windows; the separate storage repair must remain compatible with replaying rows that the browser then skips locally.

Count-trigger and time-trigger progress must remain independent. The first regression held `hasNext()` at 1,050,000 results until an actual elapsed-time progress record arrived, then drained to 1,100,000. Before the fix, the time update moved the next count boundary: progress was `[684544, 1050000]` and omitted `1100000`. The fixed code leaves the count boundary unchanged on time-only writes; the same method and full Workbench gate pass. RED and green Surefire output are in `logs/mvnf/20260930-101516-verify.log`, `logs/mvnf/20260930-101843-verify.log`, and `logs/mvnf/20260930-102001-verify.log`.

The legacy PagedQuery detects LIMIT/OFFSET with a regular expression over arbitrary source text. Nested queries, comments, and strings can interfere. The revised browser path must leave original query text untouched rather than compose synthetic query LIMIT/OFFSET; explicit user LIMIT/OFFSET, graph fanout, comments, strings, and nested queries must keep their semantics. Load more replays the frozen original and skips results already held locally.

The namespace-order protocol blocker was reproduced and repaired: WorkbenchPageResultWriter now emits vars before namespaces for tuple/graph results, matching the frontend RecordOrder. Its initial writer RED and final module evidence are preserved. Existing unrelated ResizeObserver health and saved-row focus evidence from the completed spacing task remains preserved; it must not be silently suppressed or reported as new spacing regressions.

The first fresh browser candidate exposed a Save interaction: the unchanged saveQuery method calls Integer.valueOf on the removed limit_query form field and returns HTTP 500. This directly blocks the saved continuation acceptance path. Save/Update omission and old-cookie regressions were captured before repairing the legacy metadata boundary. Missing obsolete save metadata now uses the existing unbounded marker 0; explicit supported legacy save limits remain validated, while browser fetch batches remain independent.

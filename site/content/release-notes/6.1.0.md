RDF4J 6.1.0 includes security hardening for remote resource access, repository identifiers, Workbench credentials,
and decompression resource limits.

## Security and deployment

### Remote resource access

Remote RDF resources are now public-network-only by default. This applies to SPARQL `LOAD`, federated `SERVICE`,
`RDFLoader` URL input, Workbench URL imports, and both built-in HTTP client backends. Only HTTP and HTTPS URLs
without user-info are accepted; every DNS answer for the initial target and each redirect must be globally routable,
and HTTPS-to-HTTP redirects are rejected. Trusted local `File` and `InputStream` imports remain available.

Administrators can deliberately restore access to specific private services with comma-separated system properties:

- `org.eclipse.rdf4j.remote.allowedHosts` accepts exact host names or IP literals.
- `org.eclipse.rdf4j.remote.allowedCidrs` accepts IPv4 or IPv6 CIDR blocks.

Invalid entries fail closed. These properties do not permit other URL schemes, embedded credentials, malformed URLs
or TLS downgrades. Applications constructing HTTP clients programmatically can supply a custom
`RemoteResourceAccessPolicy` through `RDF4JHttpClientConfig.Builder.remoteResourceAccessPolicy(...)`; `RDFLoader`
and `SPARQLServiceResolver` also provide policy-aware constructors.

### Repository identifiers and diagnostics

Repository identifiers can no longer be blank, path-like, absolute, dot segments, or contain separators, NUL/control
characters. Repository directories must stay below the normalized repositories directory and must not be symbolic
links. Unsafe legacy identifiers are not migrated automatically. To recover one, stop all RDF4J processes, make a
backup, rename its repository directory to a valid identifier, update the `rep:repositoryID` value in its `config.ttl`
to the same identifier, verify ownership and permissions, and then restart RDF4J.

Server system-information pages now omit environment variables, arbitrary JVM properties, operating-system user names
and application-data paths. Retained application, Java, operating-system and aggregate-memory values are escaped before
rendering.

### Workbench credentials

Workbench no longer stores Base64 credentials readable by browser script. Its 30-day credential cookie uses AES-256-GCM
in the form `v1.<key-id>.<nonce>.<ciphertext>`, is `HttpOnly`, `SameSite=Strict`, scoped to the Workbench context, and
marked `Secure` for secure requests. Existing plaintext/Base64 cookies are deleted and users must sign in once after
upgrading. Change-server requests are POST-only and protected by a per-session CSRF token; remote managers and
repository servlet caches are isolated by HTTP session.

By default, Workbench creates `credential-keys-v1` in its application-data directory with owner-only permissions. Local
active keys rotate after 90 days, and retired keys remain available for the cookie lifetime plus 24 hours. A cluster can
instead set `org.eclipse.rdf4j.workbench.credential-key-file` to an administrator-managed, owner-only regular file.
Workbench does not rotate external keyrings. The format is ASCII:

```text
version=1
active=<active-key-id>
key=<key-id>:<created-epoch-second>:<retired-epoch-second-or->:<base64url-encoded-32-byte-key>
```

Include exactly one non-retired active key and any previous decryption keys still needed during the 31-day transition
window. Duplicate identifiers, invalid key lengths or timestamps, symlinks, unreadable files and unverifiable or
non-owner-only permissions prevent Workbench initialization.

### Decompression resource limits

Server request decompression now uses one budget for explicit content encodings, signature detection, streams, readers
and form parsing. Malformed compressed requests return HTTP 400. Limit exhaustion returns HTTP 413 before response
commitment and aborts processing after commitment. The filter accepts the following init parameters; identically named
system properties use the prefix `org.eclipse.rdf4j.http.decompression.`:

| Filter parameter | Default |
|---|---:|
| `maxExpandedFormBytes` | 16 MiB |
| `maxExpandedRequestBytes` | 4 GiB |
| `maxExpansionRatio` | 200 |
| `expansionRatioGraceBytes` | 1 MiB |

Invalid values fail filter initialization. `maxExpandedFormBytes` must not exceed the total request limit.

`RDFLoader` now shares a separate budget across every nested compression layer and ZIP entry in one load. Applications
can override these public `RDFLoaderSettings` through `ParserConfig` or the matching system-property key:

| System property | Default |
|---|---:|
| `org.eclipse.rdf4j.rio.loader.max_expanded_bytes` | 4 GiB |
| `org.eclipse.rdf4j.rio.loader.max_expansion_ratio` | 200 |
| `org.eclipse.rdf4j.rio.loader.expansion_ratio_grace_bytes` | 1 MiB |
| `org.eclipse.rdf4j.rio.loader.max_nesting_depth` | 8 |
| `org.eclipse.rdf4j.rio.loader.max_zip_entries` | 50,000 |

All ceilings are enforced limits. Administrators may lower them to suit deployment workloads. A breached RDF import
fails with a stable parse error and its repository transaction is rolled back.
